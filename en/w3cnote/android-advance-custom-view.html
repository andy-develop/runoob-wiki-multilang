1.2 Custom View

Category Android Extended Tutorial

Introduction

A custom View, as the name suggests, is neither too common nor too rare in Android development. It's not too common because developers who use ready-made solutions from Baidu/Google are quite happy with that; it's not too rare because every APP wants to make its application gorgeous.

Overview

Before starting the topic of custom View, let me first give a brief introduction to it. Although Senior Piggy also mentioned it in a previous question (The concept of View and ViewGoup), it feels a bit rough (this was written by the senior over a year ago, when I was still just a beginner!).

When Android gives us limited controls, it also provides channels for extension. By inheriting controls, we can freely enrich our APP (controls). That is to say, customization allows Android, like JS and other languages, to have a large number of open-source projects in communities such as GitHub and Juejin; good works are constantly learned and imitated. In this sense, custom View(Group) seems a must-learn. Stop right there. Of course, blindly pursuing customization is not particularly good in actual development, especially when facing adaptation issues. Although this is a bit contradictory to the previous sentence, I hope everyone has their own opinion (in fact, the blogger rarely writes custom controls, because Material Design is enough to create personalized styles; of course, what needs to be said must still be said, and the weekly blog is still an accountability to myself).

Inheritance and Constructor Methods of Custom View

Everything has a beginning. Regarding inheritance, in fact, as long as it is a subclass of View, including View itself, it is sufficient. Of course, subclasses of View (such as TextView, ImageView) already come with some attributes; please weigh the choice yourself. For customization, let's start with the constructor.

Without further ado, here is the code.

//Let's call it Method 1. public MyView(Context context) { super(context); } //Let's call it Method 2. public MyView(Context context, AttributeSet attrs) { super(context, attrs); }

If this control will be instantiated with new in Java code, Method 1 must be implemented. If the control is used directly in XML, Method 2 must be implemented. At least one of the two must be implemented. Sometimes, you can be simple and blunt: change the [code] in Method 1super(context)tothis(context,null). private String mContent; private Boolean mIsShow; private int mBackground; private int mSelect; public MyView(Context context, AttributeSet attrs) { super(context, attrs); TypedArray typedArray = context.obtainStyledAttributes(attrs,R.styleable.MyViewStyle); if(typedArray != null){ //Note here: the String type has no default value, so it must be defined properly, otherwise it will be another NullPointerException trick. mContent = typedArray.getString(R.styleable.MyViewStyle_content); mIsShow = typedArray.getBoolean(R.styleable.MyViewStyle_is_show, true); mBackground = typedArray.getColor(R.styleable.MyViewStyle_view_background, Color.RED); mSelect = typedArray.getInt(R.styleable.MyViewStyle_select, 0); } Log.d("viewStyle","content:"+mContent); Log.d("viewStyle","isShow:"+mIsShow); Log.d("viewStyle","background:"+mBackground); Log.d("viewStyle","select:"+mSelect); }

Custom Control - View - onMeasure

Since it is a control, no need to say more, it must first have its width and height. But we have clearly already defined the control's [width and height] in XML.layout_widght 与 layout_height, why do we still need to specifically override the custom control's onMeasure? As for why, see below.

A few concepts

The Android system provides us with a MeasureSpec class to help us measure View. MeasureSpec is a 32-bit int value, where the high 2 bits are the measurement mode and the low 30 bits are the measurement size. Is this binary! Yes, but rest assured, Google is quite considerate of math-impaired people. Through the methods of MeasureSpec, we can obtain the values we need.

Let's talk about measurement modes. The measurement mode can be one of the following three:

  • EXACTLY:Exact mode When we set the layout_width and layout_height attributes of the control to specific values (excluding wrap_content), the system uses this mode. (Also, the onMeasure of the View class defaults to EXACTLY mode, so if you don't override onMeasure, you can only use the default mode.)
  • AT_MOST:Maximum mode When the layout_width or layout_height attribute of the control is wrap_content, the control size generally changes with the child controls or content. At this time, the size of the control only needs to not exceed the maximum size allowed by the parent control.
  • UNSPECIFIED：It cannot determine its size measurement mode; the View can be as large as it wants. It is usually used when drawing custom Views.

After having a vague understanding of the above concepts, let's start to override this method. Perhaps you are eager, because if you had no prior understanding of custom View, you would also look as dazed as I did at first.

@Override protected void onMeasure(int widthMeasureSpec, int heightMeasureSpec) { super.onMeasure(widthMeasureSpec, heightMeasureSpec); //Set the width and height of the control. Remember that the default here is px. Remember to convert resolution for adaptation; this is not explained here. setMeasuredDimension(getSize(widthMeasureSpec),getSize(heightMeasureSpec)); } private int getSize(int measureSpec){ int result = 0; int specMode = MeasureSpec.getMode(measureSpec); int specSize = MeasureSpec.getSize(measureSpec); switch (specMode){ case MeasureSpec.EXACTLY: //When layout_width and layout_height are match_parent or fixed values, go here. result = 200; break; case MeasureSpec.AT_MOST: //When layout_width and layout_height are defined as wrap_content, go here. result = Math.min(１00,specSize); break; case MeasureSpec.UNSPECIFIED: //If no size is specified result = 400; break; } return result; }

That's it, the great work is done. By now, everyone should be familiar with View's onMeasure, but the story isn't over yet. Let's talk about the layout method.

Custom Control - View - layout

layout, as the name implies, defines the layout in which this control is placed. In fact, even if we determine the width and height of this control through onMeasure, not all widths and heights can be displayed. We still need to allocate usable space to this control through layout.

Because layout is not difficult, and understanding is enough, so I'll unceremoniously go straight to the code.

@Override public void layout(int l, int t, int r, int b) { super.layout(l, t, r, b); Log.d("layout:","l:"+l); Log.d("layout:","t:"+t); Log.d("layout:","r:"+r); Log.d("layout:","b:"+b); }

The current control's width and height is 200px, the output result is: l:48 t:48 r:248 b:248

Custom Control - View - onDraw

What should be prepared is prepared, and what should not be said has been said. Next, we are going to override our onDraw method. Since it is a custom View, it is all about being a bit more 'flashy' and having higher customization, so the onDraw method must be called.

View drawing is inseparable from Canvas. So when overriding the onDraw method, the system passes us a Canvas object. The rest is to use a self-created Paint to draw the interface we want. No more talk, here's the code, duang!

@Override protected void onDraw(Canvas canvas) { super.onDraw(canvas); Paint paint = new Paint(); canvas.drawCircle(50, 50, 50, paint); }

In this way, we simply drew a circle. Do you feel that this article on custom View ends here? Wrong! Let's do a small experiment. We add a log Log.d("myView","onDraw"); below super.onDraw(canvas);, then add an event to this control, and see what happens.

findViewById(R.id.myview).setOnClickListener(new View.OnClickListener() { @Override public void onClick(View view) { view.invalidate(); //Refresh this View } });

The invalidate method refreshes the View. When we click this control, onDraw will be called repeatedly (besides clicks, this method is often called). At the same time, this also means that the Paint in our onDraw code will be created multiple times. Hehe, do you get it now? Next, let's finally talk about custom View optimization.
