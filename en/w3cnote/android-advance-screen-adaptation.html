1.1 Common Screen Adaptation in Android

Category Android Extended Tutorial

Introduction

The joke brought about by Android open source is nothing more than compatibility issues among various models and versions of phones, which also becomes a challenge every Android developer has to face. In other words, all kinds of miscellaneous problems come without warning. This article will mainly introduce the adaptation problem among compatibility issues.

Basic Concepts

  • Screen Size

    The length of the diagonal of the screen, usually expressed in inches.

  • Resolution

    Refers to the number of pixels on the phone screen.

  • Screen Pixel Density (Pixels Per Inch)

    The number of pixels per inch. More precisely, it is the number of pixels on the diagonal divided by the screen size.

Combining the above screen factors, the Android system defines several standard DPI (PPI) values.

Resolution240X320320X480480X800720X12801080X1920

Density-independent Pixel dp

It is precisely because of different screen densities that the same pixel size appears as different lengths on different screens. The Android system uses mdpi, i.e., 160dpi, as the standard. On this screen, 1px = 1dp. Other screens are converted proportionally. In hdpi (240dpi), 1dp = 1.5px... (that is, ldpi:mdpi:hdpi:xhdpi:xxhdpi = 3:4:6:8:12).

Scale-independent Pixel sp

In development, sp is used as the unit for setting font sizes. Fonts set with this unit are affected by the system font size. It is recommended to use 12sp, 14sp, 18sp, and 22sp as font sizes.

Solving Screen Adaptation

With the basic concepts of screens in mind, fragmentation problems keep occurring in actual development. So, let's embark on the journey of screen adaptation.

Image Adaptation

In addition to what Xiao Zhu wrote in a previous article about using.9 imagesmore often we need to solve the problem of image distortion.

Android SDK image loading process

  1. The Android SDK automatically selects the corresponding resource files to render and load based on screen density. For example, if the SDK detects that your phone's resolution is xhdpi, it will first look for the corresponding image resource in the xhdpi folder;
  2. If there is no image resource in the xhdpi folder, it will look in folders with higher resolution, such as xxhdpi, until it finds an image resource with the same name, then scale it down proportionally to an xhdpi image;
  3. If the image is still not found by looking upward, it will look in lower-resolution folders, such as hdpi, until it finds an image resource with the same name, then scale it up proportionally to an xhdpi image.

In this regard, when working with the designer, try to choose larger images as much as possible, while also taking into account the current mainstream resolution screens.

Layout Adaptation

Let's start with layout_weight. layout_weight is a property of android.widget.LinearLayout. Simply put, it can only be used in child views of LinearLayout. Of course, wrap_content and match_parent are not used. I think everyone already knows how to use it; it's just that there are some cautions about using layout_weight. Qualifiers

Size Qualifier

  • Usage scenario

    Friends who have used tablets and phones have probably seen this: an app will have this situation where on a phone (smaller screen), a single-pane layout displays content. On a tablet, a two-pane mode displays more content.

  • How to use

    We can use the size qualifier (layout-large) to create a resource directory. This way, our directory structure will become like this, and we put different content into it.

    res/layout/activity_main.xml

    <LinearLayout xmlns:android="http://schemas.android.com/apk/res/android" android:orientation="vertical" android:layout_width="match_parent" android:layout_height="match_parent"> <fragment android:id="@+id/left_fragment" android:layout_height="match_parent" android:name="com.xlhgo.demo.LeftFragment" android:layout_width="match_parent" /> </LinearLayout>

    res/layout-large/activity_main.xml

    <LinearLayout xmlns:android="http://schemas.android.com/apk/res/android" android:layout_width="match_parent" android:layout_height="match_parent" android:orientation="horizontal"> <fragment android:id="@+id/left_fragment" android:layout_height="match_parent" android:layout_width="0dp" android:layout_weight="1" android:name="com.xlhgo.demo.LeftFragment" /> <fragment android:id="@+id/right_fragment" android:layout_height="match_parent" android:layout_width="0dp" android:layout_weight="1" android:name="com.xlhgo.demo.RightFragment /> </LinearLayout>

  • Notes

    This approach is only suitable before Android 3.2. After that, there is a new toy.

Smallest-width Qualifier

Based on the original size qualifier, large is rather vague, so Google Daddy brought everyone a new approach, the smallest-width qualifier.

  • How to use

    res/layout-sw600dp/activity_main.xml

    <LinearLayout xmlns:android="http://schemas.android.com/apk/res/android" android:layout_width="match_parent" android:layout_height="match_parent" android:orientation="horizontal"> <fragment android:id="@+id/left_fragment" android:layout_height="match_parent" android:layout_width="0dp" android:layout_weight="1" android:name="com.xlhgo.demo.LeftFragment" /> <fragment android:id="@+id/right_fragment" android:layout_height="match_parent" android:layout_width="0dp" android:layout_weight="1" android:name="com.xlhgo.demo.RightFragment /> </LinearLayout>

  • Analysis

    That is to say, for devices with a smallest width greater than or equal to 600dp, the system will choose the layout-sw600dp/main.xml (two-pane) layout; otherwise, the system will choose the layout/activity_main.xml (single-pane) layout.

    However, devices with Android versions lower than 3.2 do not support this technique because they cannot recognize sw600dp as a size qualifier, so we still need to use the large qualifier. In this way, there will be a file named res/layout-large/main.xml (just like res/layout-sw600dp/activity_main.xml). Hehe, Android saw through all this long ago.

Using Layout Aliases

To solve the above problem, we use layout aliases.

  • How to use:

    We move the original res/layout-sw600dp/activity_main.xml layout to the res/layout/ directory, and name it activity_main_(xxx).xml (the naming convention for xxx should ideally be standardized).

    Next, let's look at the layouts in values-large and values-sw600dp.

    <resources> <item name="main" type="layout">@layout/activity_main_(xxx)</item> </resources>

Screen Orientation Qualifier

  • res/layout-land
  • res/layout-port
  • res/layout-sw600dp-land
  • res/layout-sw600dp-port

Using dimen

Even using dp cannot completely solve the screen adaptation problem, especially easily noticeable in horizontal layouts, because different phones have different dp values for screen width and height. Therefore, no matter how you assign dp values to controls, you cannot solve adaptation well.

  • Solution

    We divide the screen width into 320 parts and height into 480 parts, then assign a value to each unit according to the actual pixels, and place them in lay_x.xml and lay_y.xml under the corresponding values-widthxheight folders.

  • Specific code

    import java.io.File; import java.io.FileNotFoundException; import java.io.FileOutputStream; import java.io.PrintWriter; /** * Created by xlh on 2016/12/4. */ public class MakeXml { private final static String rootPath = "F:\\layoutroot\\values-{0}x{1}\\"; //You can change it according to your own situation. private final static float dw = 320f; private final static float dh = 480f; private final static String WTemplate = "<dimen name=\"x{0}\">{1}px</dimen>\n"; private final static String HTemplate = "<dimen name=\"y{0}\">{1}px</dimen>\n"; public static void main(String[] args) { makeString(320, 480); makeString(480, 800); makeString(480, 854); makeString(540, 960); makeString(600, 1024); makeString(720, 1184); makeString(720, 1196); makeString(720, 1280); makeString(768, 1024); makeString(800, 1280); makeString(1080, 1812); makeString(1080, 1920); makeString(1440, 2560); } public static void makeString(int w, int h) { StringBuffer sb = new StringBuffer(); sb.append("<?xml version=\"1.0\" encoding=\"utf-8\"?>\n"); sb.append("<resources>"); float cellw = w / dw; for (int i = 1; i < 320; i++) { sb.append(WTemplate.replace("{0}", i + "").replace("{1}", change(cellw * i) + "")); } sb.append(WTemplate.replace("{0}", "320").replace("{1}", w + "")); sb.append("</resources>"); StringBuffer sb2 = new StringBuffer(); sb2.append("<?xml version=\"1.0\" encoding=\"utf-8\"?>\n"); sb2.append("<resources>"); float cellh = h / dh; for (int i = 1; i < 480; i++) { sb2.append(HTemplate.replace("{0}", i + "").replace("{1}", change(cellh * i) + "")); } sb2.append(HTemplate.replace("{0}", "480").replace("{1}", h + "")); sb2.append("</resources>"); String path = rootPath.replace("{0}", h + "").replace("{1}", w + ""); File rootFile = new File(path); if (!rootFile.exists()) { rootFile.mkdirs(); } File layxFile = new File(path + "lay_x.xml"); File layyFile = new File(path + "lay_y.xml"); try { PrintWriter pw = new PrintWriter(new FileOutputStream(layxFile)); pw.print(sb.toString()); pw.close(); pw = new PrintWriter(new FileOutputStream(layyFile)); pw.print(sb2.toString()); pw.close(); } catch (FileNotFoundException e) { e.printStackTrace(); } } public static float change(float a) { int temp = (int) (a * 100); return temp / 100f; } }

    Correspondingly, every directory has lay_x.xml and lay_y.xml.

    The code inside is also very regular.

  • How to use

    With these files, it is very convenient to use. Suppose the design image given to me by the designer is 320*480, then you can directly call it like this: android:layout_xxx="@dimen/xxxx"

Percentage Layout

Regarding the percentage layout, if I remember correctly, it was something new in early 2015. Because it is Google's own child, I won't say much; let me directly give the official link:android-percent-support-lib-sample

It is nothing more than a percentage layout. If you can communicate properly with the designer, it will be a good choice in Android development.

<?xml version="1.0" encoding="utf-8"?> <android.support.percent.PercentRelativeLayout xmlns:android="http://schemas.android.com/apk/res/android" xmlns:app="http://schemas.android.com/apk/res-auto" android:layout_width="match_parent" android:layout_height="wrap_content"> <Button android:layout_width="0dp" android:layout_height="wrap_content" android:text="30%" app:layout_widthPercent="30%"/> <Button android:layout_width="0dp" android:layout_height="wrap_content" android:layout_alignParentRight="true" android:text="20%" app:layout_widthPercent="20%"/> </android.support.percent.PercentRelativeLayout>
