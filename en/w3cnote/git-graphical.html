Basic Usage

The four commands above copy files between the working directory, the staging directory (also called the index), and the repository.

  • git add filesPut the current file into the staging area.
  • git commitGenerate a snapshot of the staging area and commit.
  • git reset -- filesUsed to undo the lastgit add files, you can also usegit resetto undo all files in the staging area.
  • git checkout -- filesCopy files from the staging area to the working directory to discard local modifications.

You can usegit reset -p, git checkout -p, or git add -pto enter interactive mode.

You can also skip the staging area and directly retrieve files from the repository or directly commit code.

  • git commit -a Equivalent to runninggit addadding all files in the current directory to the staging area and then running.git commit.
  • git commit filesMake a commit that includes the last commit plus a snapshot of the files in the working directory. And the files are added to the staging area.
  • git checkout HEAD -- filesRoll back to copy the last commit.

Another example is a detached HEAD commit, which will be discussed later.

Checkout

The checkout command is used to copy files from a historical commit (or staging area) to the working directory, and can also be used to switch branches.

When a file name is given (or the -p option is enabled, or both the file name and -p option are enabled together), git copies files from the specified commit to the staging area and working directory. For example,git checkout HEAD~ foo.cwill, from the commit nodeHEAD~(i.e., the parent node of the current commit node),foo.ccopy the file to the working directory and add it to the staging area. (If no commit node is specified in the command, the content is copied from the staging area.) Note that the current branch does not change.

When no file name is specified, but a (local) branch is given, then theHEADidentifier moves to that branch (that is, we "switch" to that branch), and then the contents of the staging area and working directory will beHEADconsistent with the corresponding commit node. All files in the new commit node (a47c3 in the figure below) will be copied (to the staging area and working directory); files that exist only in the old commit node (ed489) will be deleted; files that belong to neither of the above will be ignored and unaffected.

If neither a file name nor a branch name is specified, but rather a tag, remote branch, SHA-1 value, or a similarmaster~3thing, you get an anonymous branch, calleddetached HEAD(detachedHEADidentifier). This makes it convenient to switch between historical versions. For example, if you want to compile git version 1.6.6.1, you can rungit checkout v1.6.6.1(this is a tag, not a branch name), compile, install, and then switch back to another branch, for examplegit checkout master. However, when a commit operation involves a "detached HEAD", its behavior is slightly different; see below for details.

Reset

The reset command points the current branch to another location, and selectively changes the working directory and index. It is also used to copy files from the historical repository to the index without changing the working directory.

If no option is given, the current branch points to that commit. If the--hardoption is used, the working directory is also updated; if the--softoption is used, neither changes.

If no commit version number is given, by defaultHEAD. In this way, the branch pointer remains unchanged, but the index is rolled back to the last commit; if the--hardoption is used, the working directory is also the same. If a file name is given (or-poption), the effect is similar to checkout with a file name, except that the index is updated.

Merge

The merge command merges different branches. Before merging, the index must be identical to the current commit. If another branch is the grandparent of the current commit, the merge command will do nothing. The other case is if the current commit is the grandparent of another branch, resulting in afast-forwardmerge. The pointer simply moves, and does not generate a new commit.

Otherwise, it is a real merge. By default, the current commit (ed489as shown below) and another commit (33104) and their common grandparent node (b325c) perform athree-way merge.. The result is that the current directory and index are saved first, and then together with the parent node33104a new commit is made.

Cherry Pick

The cherry-pick command "copies" a commit node and makes an identical new commit on the current branch.

Rebase

Rebasing is an alternative to the merge command. Merge combines two parent branches into one commit, and the commit history is not linear. Rebasing replays the history of another branch on the current branch, making the commit history linear. In essence, this is an automated cherry-pick that linearizes.

The above commands are all performed on thetopicbranch, not themasterbranch; on themasterbranch they are replayed, and the branch is pointed to the new node. Note that the old commits are not referenced and will be reclaimed.

To limit the rollback range, use the--ontooption. The following command, on themasterbranch, replays the current branch from169a6the recent commits since, that is,2c33a。

There is alsogit rebase --interactiveto make it more convenient for you to complete some complex operations, such as discarding, rearranging, modifying, and merging commits. There are no pictures illustrating these; see here for details:git-rebase(1)

Technical Notes

File contents are not actually stored in the index (.git/index) or in commit objects, but are stored separately in the database as blobs (.git/objects), and are verified with SHA-1 values. The index file uses identification codes to list relevant blob files and other data. For commits, they are stored in a tree (treeform, also identified by the corresponding hash value. Trees correspond to folders in the working directory, and the trees or blob objects contained in a tree correspond to the corresponding subdirectories and files. Each commit stores the identification code of its parent tree.

If you commit with detached HEAD, the last commit will be referenced by the reflog for HEAD. But it becomes invalid after a while and is eventually reclaimed, similar togit commit --amendorgit rebasein nature.
