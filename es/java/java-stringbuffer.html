Clases StringBuffer y StringBuilder de Java

Cuando necesites modificar cadenas, debes usar las clases StringBuffer y StringBuilder.

A diferencia de la clase String, los objetos de las clases StringBuffer y StringBuilder pueden modificarse múltiples veces sin generar nuevos objetos sin usar.

Al usar la clase StringBuffer, cada operación se realiza sobre el propio objeto StringBuffer en lugar de generar un objeto nuevo, por lo que si necesitas modificar cadenas, se recomienda usar StringBuffer.

La clase StringBuilder se introdujo en Java 5. La mayor diferencia con StringBuffer es que los métodos de StringBuilder no son seguros para subprocesos (no permiten acceso sincronizado).

Dado que StringBuilder tiene ventaja de velocidad sobre StringBuffer, se recomienda usar StringBuilder en la mayoría de los casos.

Ejemplo

public class RunoobTest{ public static void main(String[] args){ StringBuilder sb = new StringBuilder(10); sb.append("Runoob.."); System.out.println(sb); sb.append("!"); System.out.println(sb); sb.insert(8, "Java"); System.out.println(sb); sb.delete(5,8); System.out.println(sb); } }

El resultado de compilar y ejecutar el ejemplo anterior es el siguiente:

Runoob..
Runoob..!
Runoob..Java!
RunooJava!

Sin embargo, cuando la aplicación requiere seguridad para subprocesos, se debe usar la clase StringBuffer.

Código del archivo Test.java:

public class Test{ public static void main(String[] args){ StringBuffer sBuffer = new StringBuffer("Sitio web oficial de Runoob:"); sBuffer.append("www"); sBuffer.append(".runoob"); sBuffer.append(".com"); System.out.println(sBuffer); } }

    En Java, StringBuffer y String tienen ciertas diferencias. Primero, String está modificado por final, por lo que su longitud es inmutable. Incluso si se llama al método concat de String, lo que hace es concatenar las cadenas y crear un nuevo objeto, asignando el valor de la String concatenada al nuevo objeto. En cambio, la longitud de StringBuffer es variable; se llama al método append de StringBuffer para cambiar la longitud de StringBuffer. Además, comparado con StringBuffer, cuando String cambia de longitud, consume mucha memoria.

    ¿Cuál es el escenario de aplicación adecuado para StringBuilder y StringBuffer en Java?

    La respuesta más simple es que StringBuffer prácticamente no tiene escenarios de uso; deberías elegir usar StringBuilder en todos los casos, a menos que realmente te encuentres con un escenario que requiera seguridad para subprocesos. Si lo encuentras, no olvides dejar un comentario aquí para avisarme.

    Además, un punto adicional: sobre la seguridad para subprocesos, incluso si realmente te encuentras con ese escenario, lamentablemente, en el 99.99....99% de los casos probablemente no sea necesario elegir StringBuffer, porque la seguridad para subprocesos de StringBuffer solo garantiza que la JVM no lance excepciones y continúe ejecutándose sin problemas; no garantiza la corrección lógica ni el orden correcto de las llamadas. La mayoría de las veces, lo que necesitamos no es solo seguridad para subprocesos, sino bloqueos (locks).

    Finalmente, ¿por qué existe StringBuffer? Si realmente no tiene valor, ¿por qué JDK proporciona esta clase? La respuesta es muy simple: porque al principio no existía StringBuilder. La gente de Sun, por alguna consideración estúpida, decidió que StringBuffer fuera seguro para subprocesos. Unos 10 años después, la gente finalmente se dio cuenta de lo estúpida que fue esa decisión, y de cuánto contribuyó esa decisión estúpida al rumor de que Java era lento durante esos 10 años. Así que, en JDK 1.5, finalmente decidieron proporcionar una implementación de StringBuffer que no fuera segura para subprocesos, y la llamaron StringBuilder. Por cierto, parece que javac también comenzó aproximadamente desde esta versión a reescribir implícitamente todas las operaciones de String unidas con el signo más (+) a StringBuilder. Es decir, desde JDK 1.5, concatenar cadenas con el signo más ya no tiene ninguna pérdida de rendimiento.

    Como han señalado muchos comentarios, lo que dije antes, "concatenar cadenas con el signo más ya no tiene ninguna pérdida de rendimiento", no es riguroso. Estrictamente hablando, si no hay bucles, concatenar cadenas con el signo más en una sola línea no tiene pérdida de rendimiento; el compilador de Java lo reemplaza implícitamente por StringBuilder. Pero en presencia de bucles, el compilador no puede hacer un reemplazo lo suficientemente inteligente, y todavía habrá una pérdida de rendimiento innecesaria. Por lo tanto, al concatenar cadenas en un bucle, es mejor usar StringBuilder honestamente.
