Sistema de memoria de Hermes Agent

La capacidad diferenciadora más importante de Hermes no es la invocación de herramientas, sino querealmente te recuerda.。

La mayoría de las herramientas de IA empiezan desde cero en cada conversación: hoy dedicas una hora a enseñarle la estructura de tu proyecto, las convenciones de nomenclatura y el flujo de despliegue, y mañana abres una sesión nueva y todo se pierde.

Este capítulo analiza en profundidad cómo Hermes resuelve este problema mediante una estructura de memoria de tres capas, y cómo el agente gestiona la memoria de forma autónoma, logrando búsqueda y recuperación entre sesiones.

Arquitectura de memoria de tres capas

Hermes utiliza una estructura de memoria de tres capas, independientes entre sí y funcionalmente complementarias, para almacenar y recuperar información.

La idea central del diseño de tres capas:La información importante de alta frecuencia reside permanentemente en el contexto, la información histórica de baja frecuencia se recupera bajo demanda, y los patrones profundos los infiere la IA automáticamente.—logrando un equilibrio entre la capacidad de memoria y el coste de tokens.

┌─────────────────────────────────────────────────┐
│       第一层：持久记忆（Persistent Memory）        │
│  MEMORY.md（环境事实）+ USER.md（用户画像）          │
│  → 每次会话启动时自动注入系统提示词，始终可见          │
├─────────────────────────────────────────────────┤
│       第二层：情节日志（Session History）            │
│  SQLite + FTS5 全文检索，存储所有历史对话             │
│  → Agent 主动搜索时按需加载，不占用固定 Token         │
├─────────────────────────────────────────────────┤
│       第三层：用户建模（Honcho，可选）               │
│  辩证推理引擎，提取跨会话模式、偏好与目标              │
│  → 比你亲口说出来的更深层地理解你                     │
└─────────────────────────────────────────────────┘
Nivel de memoriaUbicación de almacenamientoCapacidadMétodo de cargaUso
Memoria persistenteArchivos Markdown en `~/.hermes/memories/`~1300 tokens en totalSe inyecta automáticamente en el prompt del sistema al iniciar la sesiónHechos clave, siempre visibles
Registro episódicoBase de datos SQLite + archivos de transcripción JSONLIlimitado (todas las conversaciones históricas)El agente busca bajo demanda, con búsqueda de texto completo FTS5Para encontrar discusiones históricas específicas
Modelado de usuarios con HonchoAPI del servidor HonchoAislado por agenteInyección de inferencia en segundo plano cada turno / cada N turnosDeducción automática de preferencias y objetivos profundos

Las tres capas no se sustituyen entre sí, sino que se complementan. La memoria persistente responde «siempre necesito saber esto», el registro episódico responde «¿hablamos de este tema la semana pasada?», y Honcho responde «¿qué es lo que realmente deseas?».

Archivos de memoria persistente

La memoria persistente es la primera capa del sistema de memoria de Hermes, y también la más básica.

Se compone de dos archivos Markdown guardados en~/.hermes/memories/`~/.hermes/memories/`.

Dos archivos principales

Los dos archivos tienen funciones distintas y no se superponen.

ArchivoPropósitoLímite de caracteresAproximadamente igual a
MEMORY.mdNotas personales del agente: hechos del entorno, normas del proyecto, cosas aprendidas en el trabajo.2200 caracteres~800 tokens
USER.mdPerfil del usuario: tus preferencias, estilo de comunicación, hábitos de trabajo, nivel de habilidades.1375 caracteres~500 tokens

El límite de caracteres es una decisión deliberada: garantiza que el contenido de la memoria se mantenga conciso y enfocado. Si una nueva entrada supera el límite, la herramienta `memory` devuelve un error para que el agente libere espacio antes de escribir, en lugar de descartar silenciosamente entradas antiguas.

Cómo se inyecta la memoria en el prompt del sistema

Cada vez que se inicia una sesión, el contenido de los dos archivos se inyecta en el prompt del sistema con un formato fijo, como se muestra a continuación:

══════════════════════════════════════════════
MEMORY（Agent 个人笔记）[67% — 1,474/2,200 字符]
══════════════════════════════════════════════
用户的项目是位于 ~/code/myapi 的 Rust Web 服务，使用 Axum + SQLx
§
本机运行 Ubuntu 22.04，已安装 Docker 和 Podman
§
用户偏好简洁回复，不喜欢冗长解释

Aquí hay varios detalles de diseño clave:

Modo de instantánea congelada: el contenido de la memoria en el prompt del sistema se captura una vez al inicio de la sesión y no se actualiza a mitad de sesión.

Es un diseño intencional: mantener válida la caché de prefijo (Prompt Cache) del LLM y reducir el coste de tokens.

El agente modifica la memoria durante la sesión; los cambios se escriben inmediatamente en el disco, pero hay que esperaral inicio de la próxima sesiónpara que aparezcan en el contexto.

El porcentaje de uso es visible：[67% — 1,474/2,200]Permite que el agente conozca en todo momento la capacidad restante y organice la memoria proactivamente cuando se acerca al límite.

§ como separador de entradas: cada memoria se separa con §, y cada entrada puede ser texto de varias líneas.

Cómo el agente gestiona la memoria

El agente utiliza la herramienta integradamemory`memory` para gestionar la memoria, que admite tres operaciones.

OperaciónDescripciónParámetros
addAñadir una entrada de memoriatarget（memory/user）、content
replaceReemplazar una entrada existente (localización por coincidencia de subcadena)target、old_text、content
removeEliminar una entrada existente (localización por coincidencia de subcadena)target、old_text

Nota:No hay operación `read`—el contenido de la memoria ya se inyecta en el prompt del sistema al iniciar la sesión, y el agente lo ve directamente en el contexto, sin necesidad de leerlo adicionalmente.

replace 和 removeUso decoincidencia de subcadenaspara localizar entradas, sin necesidad de proporcionar el texto completo de la entrada:

Ejemplo

# Escenario: la memoria actual contiene "el usuario prefiere el tema oscuro en todos sus editores"
# Ahora hay que actualizarla a una versión más precisa.
# Usa la coincidencia de subcadenas para localizar: basta con proporcionar un fragmento que la identifique de forma única.

memory(
    action="replace",
    target="memory",
    old_text="tema oscuro",  # Una subcadena única es suficiente para localizar la entrada original.
    content="el usuario usa el tema claro en VS Code y el tema oscuro en la terminal"  # Nuevo contenido después del reemplazo.
)

Si la subcadena coincide con varias entradas, la herramienta devuelve un error y solicita una cadena de coincidencia más precisa.

Qué recordar y qué no recordar

El agente juzga automáticamente y guarda la información valiosa; normalmente no necesitas pedirlo explícitamente.

Pero conocer el criterio de juicio te ayuda a entender el comportamiento del agente y a guiarlo manualmente cuando sea necesario.

Debería guardarse proactivamente en `memory` (entorno y trabajo)

Los siguientes tipos de información hacen que el agente escriba en `MEMORY.md`:

TipoEjemplo
Hechos del entornoEste equipo ejecuta Debian 12, PostgreSQL 16, y Docker se sustituye por Podman.
Normas del proyecto`~/code/api` usa Go 1.22, consultas con sqlc, rutas con chi; para las pruebas se utiliza `make test`.
Experiencia con herramientasEl puerto SSH del servidor de staging es 2222, no 22; la clave está en `~/.ssh/staging_ed25519`.
Registro de correccionesNo uses sudo para ejecutar comandos de Docker; el usuario ya está en el grupo docker
Completar el trabajo2026-01-15 Se completó la migración de la base de datos de MySQL a PostgreSQL

Debería guardarse proactivamente en `user` (sobre ti)

Los siguientes tipos de información activan que el Agent escriba en USER.md:

TipoEjemplo
Información de identidadNombre, cargo, zona horaria
Preferencias de comunicaciónPrefiere respuestas concisas, sin necesidad de explicar pasos obvios
AversionesNo añadir demasiados comentarios en el código
Hábitos de trabajoNo revisa mensajes antes de las 3 de la tarde
Nivel de habilidadesFamiliarizado con Rust y Python; Go es recién aprendido

Contenido que no se debe guardar

El siguiente contenido no merece ocupar espacio de memoria valioso:

TipoEjemploRazón
Demasiado generalEl usuario tiene un proyectoSin información útil, no se puede reutilizar
Se puede consultar en cualquier momentoPython 3.12 soporta anidamiento de f-stringsBasta con buscarlo, no merece ocupar espacio
Datos crudosFragmentos largos de logs, bloques de código, tablas de datosExcede el límite de caracteres; la memoria estructurada es más útil
Contenido temporalRuta del archivo temporal de esta depuraciónNo se usará la próxima vez
Contenido ya presente en el contextoInformación que ya existe en SOUL.md y AGENTS.md del proyectoLa inyección repetida desperdicia tokens

Buena memoria vs. mala memoria

Con la misma información, bien escrita puede valer por diez entradas; mal escrita, no tiene ningún valor.

CalificaciónEjemploComentario
好El usuario tiene macOS 14 Sonoma, Homebrew, Docker Desktop; el shell es zsh con oh-my-zsh; el editor es VS Code + keybindings de VimAlta densidad de información, hechos relacionados agrupados
好El proyecto ~/code/api usa Go 1.22, sqlc para consultas de BD, router chi. Pruebas: make test. CI: GitHub ActionsEspecificaciones concretas y ejecutables
好El servidor de staging (10.0.1.50) usa puerto SSH 2222, no 22; clave ~/.ssh/staging_ed25519Lecciones aprendidas con contexto, evita caer en errores

差El 5 de enero de 2026, el usuario me pidió revisar su proyecto en ~/code/api; descubrí que usa Go 1.22...Demasiado extenso, la información clave queda ahogada en la narración

Gestión de la capacidad de memoria

Los archivos de memoria tienen un límite estricto de caracteres; el Agent debe organizar proactivamente al acercarse al límite.

Qué ocurre cuando se acerca al límite

Cuando una nueva entrada superaría el límite de caracteres, la herramienta devuelve un error en lugar de truncar silenciosamente:

{
  "success": false,
  "error": "Memory 已用 2,100/2,200 字符。新条目（250 字符）会超出上限。
            请先整理：用 replace 合并重叠条目，或 remove 过时条目，
            再重试——在同一轮对话中完成。",
  "current_entries": [
    "用户的 macOS 14 Sonoma，Homebrew，Docker Desktop",
    "项目 ~/code/api 使用 Go 1.22，sqlc 做 DB 查询"
  ],
  "usage": "2,100/2,200"
}

Tras recibir este error, lo correcto que debe hacer el Agent es:

  1. Leer todas las entradas actuales (ya incluidas en la respuesta de error)
  2. Identificar entradas que se puedan eliminar o combinar
  3. 用 replaceFusionar varias entradas relacionadas en una versión más refinada
  4. Luego reintentar añadir la nueva entrada

Mejores prácticas: cuando el prompt del sistema muestre que el uso de memoria supera el 80 %, organiza proactivamente; no esperes al error. Prevenir siempre ahorra más tokens que remediar.

Referencia de capacidad

AlmacenamientoLímiteNúmero típico de entradas
MEMORY.md2 200 caracteres8–15 entradas
USER.md1 375 caracteres5–10 entradas

Controlar los permisos de escritura de memoria

Por defecto, el Agent puede escribir libremente en la memoria; incluidala revisión de automejora activada automáticamente en segundo plano(se ejecuta en segundo plano al terminar una ronda de conversación, destilando memoria y habilidades).

Si deseas revisar antes de que cualquier contenido se escriba en la memoria, puedes activar la aprobación de escritura.

Activar la aprobación de escritura

Basta con configurarlo en el archivo de configuración:

Ejemplo

# Ruta del archivo: ~/.hermes/config.yaml
# Activar aprobación de escritura en memoria: todas las operaciones de escritura requieren aprobación manual
memory:
  write_approval: true   # Por defecto false (escritura libre)

Cambios de comportamiento tras activarlo

EscenarioComportamiento
El Agent quiere escribir memoria durante una interacción CLITe pide aprobación en línea dentro de la terminal
Plataforma de mensajería / revisión automática en segundo planoLa escritura se pone en espera, a la espera de tu aprobación manual

Comandos de gestión de aprobaciones

Usa los siguientes comandos de barra para gestionar las escrituras de memoria pendientes:

Ejemplo

# Ver escrituras de memoria pendientes (las activadas automáticamente se marcan [auto])
/memory pending

# Aprobar la escritura del ID especificado, o aprobar todas
/memory approve <id>
/memory approve all

# Rechazar la escritura del ID especificado, o rechazar todas
/memory reject <id>
/memory reject all

# Activar o desactivar la aprobación en tiempo de ejecución (el ajuste se guarda de forma persistente)
/memory approval on
/memory approval off

Casos de uso: si el Agent guardó una suposición incorrecta sobre ti, o si quieres control total sobre el contenido de la memoria, activar write_approval es la forma más directa.

Sobre la revisión de automejora en segundo plano

Al terminar cada ronda de conversación, Hermes ejecuta en segundo plano una revisión de automejora (background review), analiza la conversación y extrae memorias o habilidades que valga la pena conservar.

Por defecto se muestra una línea de aviso en el chatMemory updated。

Puedes ajustar el nivel de detalle de las notificaciones:

Ejemplo

# Ruta del archivo: ~/.hermes/config.yaml
# Controla el nivel de detalle de notificación de la revisión en segundo plano
display:
  memory_notifications: on      # off | on (predeterminado) | verbose
值Efecto
offNo muestra notificación, pero la revisión sigue ejecutándose y escribiendo
on (predeterminado)Aviso breve, como Memory updated
verboseIncluye vista previa de cambios, como Memory + el usuario prefiere respuestas concisas

Si el costo de tu modelo principal es alto, puedes hacer que la revisión en segundo plano se ejecute en un modelo más económico:

Ejemplo

# Ruta del archivo: ~/.hermes/config.yaml
# La revisión en segundo plano usa un modelo independiente para reducir costos
auxiliary:
  background_review:
    provider: openrouter
    model: google/gemini-3-flash-preview   # Por defecto auto = modelo principal

Registro episódico y búsqueda entre sesiones

La segunda capa de memoria —Registro de sesiones (Session History)— almacena el registro completo de todas las conversaciones históricas, con soporte de búsqueda de texto completo y recuperación bajo demanda.

Todas las conversaciones se guardan automáticamente

Cada sesión —ya sea de CLI, Telegram, Discord o cualquier otra plataforma— se guarda automáticamente en dos ubicaciones:

Ubicación de almacenamientoFormatoContenido
~/.hermes/state.dbBase de datos SQLite + índice de texto completo FTS5Metadatos estructurados, historial completo de mensajes (incluye llamadas a herramientas y resultados), uso de tokens, marcas de tiempo
~/.hermes/sessions/Archivos de transcripción JSONLTranscripciones de conversación en bruto, incluyen registros de llamadas a herramientas

La herramienta `session_search`

Integrada en el Agentsession_searchHerramienta que permite realizar búsquedas de texto completo en todas las conversaciones históricas.

En todo el proceso la fase de búsqueda no requiere la participación de un LLM; la realiza directamente el motor SQLite FTS5:

Flujo de trabajo:

  1. FTS5 recupera los mensajes coincidentes ordenados por relevancia
  2. Agrupa por sesión y toma las sesiones más relevantes (3 por defecto)
  3. Carga las conversaciones de cada sesión y extrae aproximadamente 100 000 caracteres alrededor de los puntos de coincidencia
  4. Genera resúmenes enfocados con un modelo de resumen ligero
  5. Devuelve al Agent el resumen y el contexto de cada sesión

Sintaxis de búsqueda soportada (estándar FTS5):

SintaxisEjemploDescripción
Búsqueda por palabras clavedocker deploymentCoincide con mensajes que contengan cualquiera de las palabras clave
Coincidencia de frase"exact phrase"Coincide exactamente con la frase completa
OR booleanodocker OR kubernetesCoincide con cualquier palabra clave
NOT booleanopython NOT javaExcluye palabras clave específicas
Comodín de prefijodeploy*Coincide con palabras que empiecen por deploy

Momento de activación: el Agente llamará automáticamente a session_search cuando menciones «lo que discutimos la última vez...» o «aquella propuesta anterior...», en lugar de pedirte que lo expliques de nuevo.

`session_search` vs. memoria persistente

Ambas funciones son complementarias, no se reemplazan entre sí:

Dimensión de comparaciónMemoria persistente (MEMORY.md / USER.md)Registro de sesiones (Session Search)
Capacidad~1,300 tokens en totalIlimitada (todo el historial de conversaciones)
VelocidadInstantánea (ya en el prompt del sistema)~20 ms (consulta FTS5)
Costo de tokensConsumo fijo por cada sesiónBajo demanda, si no se consulta no se gasta
UsoHechos clave, siempre visiblesBuscar discusiones históricas específicas
Método de gestiónEl Agente organiza proactivamenteTotalmente automático, sin intervención

MemoriaPara «siempre necesito saber esto»: hechos del entorno, preferencias del usuario, normas del proyecto.

Registro de sesionesPara «¿hablamos de este problema la semana pasada?»: buscar discusiones históricas específicas.

Gestión de sesiones

Cada sesión en el registro de sesiones puede nombrarse, restaurarse, exportarse y limpiarse.

Nombrado y restauración

Hermes genera automáticamente un título breve de sesión (3-7 palabras) después del primer turno de la conversación, ejecutándose de forma asíncrona en segundo plano sin afectar la velocidad de respuesta.

También puedes nombrarla manualmente:

Ejemplo

# Establecer título manualmente en la sesión
/title Refactorizar módulo de autenticación

Después de nombrarla, puedes restaurar la sesión directamente usando el título:

Ejemplo

# Restaurar sesión por título
hermes -c "Refactorizar módulo de autenticación"

# Restaurar la sesión más reciente
hermes --continue

# Restaurar por ID de sesión
hermes -r <session_id>

Linaje automático (Auto-Lineage): cuando una sesión pasa por compresión de contexto, Hermes crea automáticamente una sesión de continuación y la numera:

"我的项目" → "我的项目 #2" → "我的项目 #3"

Al restaurar por título, se selecciona automáticamente la sesión de continuación más reciente.

Comandos comunes de gestión de sesiones

Ejemplo

# Listar las 20 sesiones más recientes
hermes sessions list

# Filtrar por plataforma de origen
hermes sessions list --source telegram

# Mostrar más elementos
hermes sessions list --limit 50

# Renombrar una sesión específica
hermes sessions rename <id> Nuevo título

# Exportar todas las sesiones a un archivo
hermes sessions export backup.jsonl

# Eliminar una sesión específica
hermes sessions delete <id>

# Limpiar sesiones antiguas de más de 30 días
hermes sessions prune --older-than 30

# Ver información estadística
hermes sessions stats

hermes sessions listEjemplo de salida:

Limpieza automática de sesiones (opcional)

De forma predeterminada, el historial de sesiones se conserva permanentemente (porque proporciona datos para session_search).

Si necesitas limpieza automática, actívala en la configuración:

Ejemplo

# Ruta del archivo: ~/.hermes/config.yaml
# Habilitar limpieza automática de sesiones (desactivada por defecto)
sessions:
  auto_prune: true        # Por defecto false
  retention_days: 90      # Conservar los últimos 90 días
  vacuum_after_prune: true
  min_interval_hours: 24

Modelado de usuarios con Honcho

Honcho es un backend de memoria nativo de IA desarrollado por Plastic Labs, integrado en Hermes como plugin.

No reemplaza a MEMORY.md ni a USER.md, sino que sobre ellosañade una capa de razonamiento dialéctico—mediante el análisis de tus patrones de conversación, infiere automáticamente preferencias, objetivos y hábitos que no has expresado explícitamente.

A diferencia de la curación manual de MEMORY.md, Honcho es totalmente automático: después de cada turno de conversación (con frecuencia configurable), razona en segundo plano y acumula una comprensión cada vez más profunda de ti.

Comparación entre Honcho y la memoria integrada

CapacidadMemoria integradaHoncho
Persistencia entre sesionesArchivos localesAPI del servidor
Perfil de usuarioCuración manual (USER.md)Razonamiento dialéctico automático
Resumen de sesión—Inyección de contexto a nivel de sesión
Aislamiento de múltiples agentes—Modelado separado por agente
Búsqueda semánticaTexto completo FTS5Basada en conclusiones de razonamiento

Inyección de contexto en dos capas

En cada turno de conversación, Honcho compone dos capas de contexto para inyectarlas en el prompt del sistema:

Capa base (Base Context): resumen de la sesión + representación del usuario + Peer Card del usuario + autorrepresentación de la IA. Se actualiza según contextCadence (cada N turnos). Esta es la capa de «quién es este usuario».

Capa dialéctica (Dialectic Supplement): generada por inferencia en tiempo real del motor LLM de Honcho, se centra en «qué es lo más relevante en este momento». Se actualiza según dialecticCadence.

Dos modos de inicio para el razonamiento dialéctico:

ModoCondiciónMétodo de consulta
Arranque en fríoSin datos históricosConsulta genérica: «¿Quién es este usuario? ¿Cuáles son sus preferencias, objetivos y forma de trabajar?»
Arranque en calienteCon datos históricosConsulta centrada en la sesión: «Según lo discutido en esta sesión, ¿cuál es el contexto más relevante sobre este usuario?»

Tres perillas de ajuste independientes

ParámetroQué controlaValor predeterminado
contextCadenceIntervalo de actualización de la capa base (llama a la API cada N turnos)1
dialecticCadenceIntervalo de actualización de la capa dialéctica (llama al LLM cada N turnos)2 (recomendado 1-5)
dialecticDepthProfundidad de razonamiento de cada razonamiento dialéctico (1-3 pasadas)1

Las tres perillas son completamente independientes: puedes actualizar la capa base con alta frecuencia, ejecutar el razonamiento dialéctico con baja frecuencia, o al revés:

Ejemplo

{
  "contextCadence": 1,
  "dialecticCadence": 5,
  "dialecticDepth": 2
}

La configuración anterior significa: actualizar la capa base en cada turno y realizar una inferencia dialéctica de profundidad 2 pass cada 5 turnos.

Razonamiento dialéctico multi-pass

Cuando dialecticDepth se establece en un valor mayor que 1, cada razonamiento dialéctico ejecuta múltiples llamadas al LLM:

PassTareaDescripción
Pass 0Inferencia de arranque en frío/calienteEstablecer la evaluación inicial
Pass 1AutoauditoríaIdentificar los puntos ciegos de la evaluación inicial y sintetizar evidencia de las sesiones recientes
Pass 2ConciliaciónRevisar las contradicciones de las dos rondas anteriores y producir la conclusión final sintetizada

La profundidad 3 no equivale necesariamente a 3 llamadas al LLM: si la ronda anterior ya produjo una salida de alta calidad, la siguiente ronda sale antes para ahorrar tokens.

Inicio rápido con Honcho

Ejemplo

# Configuración interactiva, seleccionar el proveedor de honcho
hermes memory setup

O configurar manualmente:

Ejemplo

# Ruta del archivo: ~/.hermes/config.yaml
# Habilitar Honcho como proveedor de memoria
memory:
  provider: honcho

# Escribir la API Key en el archivo de variables de entorno
echo 'HONCHO_API_KEY=your_key' >> ~/.hermes/.env

Obtén una API Key en honcho.dev.

Herramientas proporcionadas por Honcho

Después de activar Honcho, el Agente puede usar cinco herramientas exclusivas:

HerramientaUso
honcho_profileLeer o actualizar la Peer Card del usuario
honcho_searchBúsqueda semántica basada en conclusiones de razonamiento (fragmentos sin procesar, sin síntesis del LLM)
honcho_contextObtener el contexto completo de la sesión (resumen, representación del usuario, mensajes recientes)
honcho_reasoningLlamar a la inferencia del LLM de Honcho (puedes especificar reasoning_level)
honcho_concludeCrear o eliminar conclusiones de razonamiento

Referencia de configuración del sistema de memoria

A continuación se presenta la referencia completa de toda la configuración relacionada con la memoria, que puedes copiar directamente a tu archivo de configuración.

Ejemplo

# ============================================
# Ruta del archivo: ~/.hermes/config.yaml
# Referencia completa de configuración del sistema de memoria de Hermes
# ============================================

# --- Configuración de memoria persistente ---
memory:
  memory_enabled: true          # Si habilitar memoria persistente (MEMORY.md)
  user_profile_enabled: true    # Si habilitar perfil de usuario (USER.md)
  memory_char_limit: 2200       # Límite de caracteres de MEMORY.md (aprox. 800 tokens)
  user_char_limit: 1375         # Límite de caracteres de USER.md (aprox. 500 tokens)
  write_approval: false         # true = todas las escrituras de memoria requieren aprobación manual
  provider: honcho              # Opcional: habilitar proveedor de memoria Honcho

# --- Limpieza automática de sesiones (opcional, desactivada por defecto) ---
sessions:
  auto_prune: false             # Si limpiar automáticamente sesiones antiguas
  retention_days: 90            # Conservar sesiones de los últimos N días
  vacuum_after_prune: true      # Si recuperar espacio en disco después de la limpieza
  min_interval_hours: 24        # Intervalo mínimo entre dos limpiezas

# --- Notificaciones de revisión en segundo plano ---
display:
  memory_notifications: on      # off | on | verbose

# --- Usar un modelo más económico para la revisión en segundo plano (opcional) ---
auxiliary:
  background_review:
    provider: openrouter        # Proveedor de modelos
    model: google/gemini-3-flash-preview  # Nombre del modelo

Editar directamente los archivos de memoria

Los archivos de memoria son Markdown normal; puedes abrirlos y modificarlos directamente con un editor:

Ejemplo

# Ver contenido actual de la memoria
cat ~/.hermes/memories/MEMORY.md
cat ~/.hermes/memories/USER.md

# Abrir con un editor para modificar
nano ~/.hermes/memories/MEMORY.md

Nota: después de editar el archivo directamente, los cambios se aplicarán en el próximo inicio de sesión, no se reflejarán inmediatamente en el contexto de la sesión actual.

Seguridad y privacidad de la memoria

Escaneo de seguridad

El contenido de la memoria se somete a un escaneo de seguridad antes de escribirse para detectar ataques de inyección y patrones de robo de datos.

El sistema detectará los siguientes patrones de amenaza:

Tipo de amenazaContenido detectado
Inyección de promptPatrones de inyección que intentan sobrescribir las instrucciones del sistema del agente
Robo de credencialesInstrucciones que inducen al agente a filtrar API Keys o Tokens
Instalación de backdoorInstrucciones de instalación de backdoors SSH o acceso remoto
Caracteres ocultosCaracteres Unicode invisibles (espacios de ancho cero, anulaciones direccionales, etc.)

El contenido que coincida con patrones de amenaza serárechazado al escribirse。

Enmascaramiento de información sensible en los registros

La información sensible como API Keys y Tokens se desensibiliza automáticamente en todos los archivos de registro; incluso si aparece en la salida de herramientas, no se registra en texto plano:

Ejemplo

# Ruta del archivo: ~/.hermes/config.yaml
# Activado por defecto, la información sensible se enmascara automáticamente
security:
  redact_secrets: true

Almacenamiento local de datos

Todos los datos de memoria (MEMORY.md, USER.md, state.db) se almacenan localmente por defecto en el~/.hermes/directorio, no se suben a la nube.

Al optar por usar Honcho, los datos de conversación se envían a los servidores de Honcho para su procesamiento; es una compensación deliberada: intercambiar la carga de datos por una capacidad de razonamiento más profunda.
