7.1.1 Lo que se debe aprender en programación de redes Android y el estudio del protocolo HTTP

Categoría Tutorial básico de introducción a Android

Introducción a esta sección:

Sin darnos cuenta, finalmente hemos llegado al capítulo de programación de redes en Android. Lo que hicimos antes eran juegos de un solo jugador, seguro que no es suficiente, ¿verdad? A partir de esta sección aprenderemos algunas cosas relacionadas con la programación de redes en Android: ¿qué se necesita hacer en la programación de redes en Android? El estudio del protocolo HTTP, el uso de las clases integradas de análisis JSON para analizar JSON, varias formas comunes de análisis XML, el uso de HttpURLConnection y HttpClient, la carga y descarga de archivos; el uso de WebService, WebView, comunicación por Socket, etc.

Además, somos el cliente; el contenido del servidor no está dentro de nuestro alcance, y Xiaozhu tampoco es bueno en eso. Nuestro requisito mínimo es:Ser capaz de dominar la capacidad de obtener y analizar los datos devueltos por el servidor.Bien, sin más preámbulos, ¡comencemos con el contenido de esta sección!

1. Tres formas de interacción entre Android e Internet

2. Primer encuentro con el protocolo HTTP

En el desarrollo real, cuando tratamos con el servidor, generalmente usamos comunicación basada en el protocolo HTTP, por lo que es muy importante aprender bien el protocolo HTTP. Por supuesto, no necesitamos profundizar demasiado en algunos detalles; basta con tener una comprensión general. ¡Son solo cosas conceptuales!

1) ¿Qué es el protocolo HTTP?

Respuesta: protocolo de transferencia de hipertexto (Hypertext Transfer Protocol), un protocolo de capa de aplicación del protocolo TCP/IP, utilizado para definir el proceso de intercambio de datos entre el navegador web y el servidor web. Después de que el cliente se conecta al servidor web, si desea obtener algún recurso web en el servidor web, debe cumplir con un cierto formato de comunicación. El protocolo HTTP se utiliza para definir el formato de comunicación entre el cliente y el servidor web.

2) Diferencias entre HTTP 1.0 y HTTP 1.1

Respuesta: En el protocolo 1.0, después de que el cliente establece una conexión con el servidor web, solo puede obtener un recurso web. En el protocolo 1.1, se permite que el cliente, después de establecer una conexión con el servidor web, obtenga múltiples recursos web en una sola conexión.

3) Flujo de trabajo subyacente del protocolo HTTP:

Respuesta: Primero necesitamos conocer dos términos:

  • SYN(synchronous): la señal de handshake utilizada al establecer la conexión TCP/IP
  • ACK(Acknowledgement): carácter de confirmación, confirma que los datos enviados han sido recibidos correctamente.

Luego llegamos ael protocolo de enlace de tres vías de TCP/IPEl concepto:

  • El cliente envía un paquete SYN (SYN = j) al servidor, entra en el estado SYN_SEND y luego espera la confirmación del servidor.
  • El servidor recibe el paquete SYN, confirma el SYN del cliente (ACK = j + 1) y, al mismo tiempo, también envía un paquete SYN (SYN = k), es decir, un paquete SYN + ACK. El servidor entra en el estado SYN_RECV.
  • El cliente recibe el paquete SYN + ACK, envía un paquete de confirmación ACK (ACK = k + 1) al servidor. Una vez enviado, el cliente y el servidor entran en el estado ESTABLISHED, completando el protocolo de enlace de tres vías, y luego ambos comienzan a transmitir datos.

Si aún no está claro, veamos el diagrama esquemático del protocolo de enlace de tres vías:

Lo has entendido, ¿verdad? Entonces echemos un vistazo al flujo de una operación HTTP:

  • El usuario hace clic en la URL (hipervínculo) en el navegador, y el navegador web establece una conexión con el servidor web.
  • Después de establecer la conexión, el cliente envía una solicitud al servidor. El formato de la solicitud es: Identificador Uniforme de Recursos (URL) + número de versión del protocolo (generalmente 1.1) + información MIME (varios encabezados de mensaje) + una línea vacía.
  • Después de recibir la solicitud, el servidor proporciona la información de respuesta correspondiente. El formato de respuesta es: número de versión del protocolo + línea de estado (resultado del procesamiento) + varios encabezados de información + línea vacía + contenido de entidad (por ejemplo, el HTML devuelto).
  • El cliente recibe la información devuelta por el servidor, la muestra a través del navegador y luego se desconecta del servidor. Por supuesto, si ocurre un error en algún paso del proceso, el mensaje de error se devolverá al cliente y se mostrará, como por ejemplo: ¡el clásico error 404!

4) Proceso de negocio del protocolo HTTP

5) Varios métodos de solicitud de HTTP

En el desarrollo real, los métodos que usamos con más frecuencia son GET y POST, pero en el desarrollo real también se pueden usar otros métodos de solicitud, como PUT. De hecho, Xiaozhu lo ha usado en sus proyectos reales. A continuación, para conveniencia de todos, enumeremos todos los métodos de solicitud:

  • Get: Solicita obtener el recurso identificado por Request-URI
  • POST: Adjunta nuevos datos al recurso identificado por Request-URI
  • HEADSolicita obtener el encabezado de información de respuesta del recurso identificado por Request-URI
  • PUT: Solicita al servidor almacenar un recurso, usando Request-URI como su identificador
  • DELETE: Solicita al servidor eliminar el recurso identificado por Request-URI
  • TRACE: Solicita al servidor devolver la información de solicitud recibida, utilizada principalmente para pruebas o diagnóstico
  • CONNECT: Reservado para uso futuro
  • OPTIONS: Solicita consultar el rendimiento del servidor o consultar las opciones relacionadas con el recurso

6) Comparación entre GET y POST

Los dos más utilizados, ¡por supuesto hay que hacer una comparación!

  • GET: Se lleva al servidor los datos en forma de '?' después de la dirección URL de la solicitud, separando múltiples datos con '&'. Sin embargo, la capacidad de datos generalmente no puede superar los 2K. Por ejemplo: http://xxx?username=...&pawd=... Este es el método GET.
  • POST: Este puede enviar datos al servidor en el contenido de la entidad de la solicitud, sin límite de cantidad en la transmisión.
  • Además, hay que decir una cosa: estos dos se utilizan para enviar datos, solo que el mecanismo de envío es diferente. ¡No creas lo que se dice en Internet: 'GET obtiene datos del servidor, POST envía datos al servidor'! Además, GET es de muy baja seguridad, POST es más seguro, pero su eficiencia de ejecución es mejor que la del método POST. Generalmente usamos GET para consultas y POST para agregar, eliminar o modificar datos.

7) Colección de códigos de estado HTTP

Por supuesto, estos códigos de estado son solo de referencia; en realidad,el poder de decisión está en el lado del servidor (backend).En manos del servidor, una opción es que después de la solicitud, el servidor nos devuelva el estado; u otra, que es más conveniente cuando la aplicación no necesita soportar múltiples idiomas, es devolvernos directamente un JSON con una cadena de información de resultado, y nosotros lo mostramos directamente. ¡Esto permite ahorrar bastante trabajo! A continuación se muestra la colección de códigos de estado, solo como referencia:

  • 100~199: Solicitud aceptada correctamente; el cliente debe enviar la siguiente solicitud para completar todo el proceso.
  • 200: OK, la solicitud del cliente se ha realizado correctamente.
  • 300~399: El recurso solicitado se ha movido a una nueva dirección (302, 307, 304).
  • 401: Solicitud no autorizada; este código de estado debe usarse junto con el campo de encabezado WWW-Authenticate.
  • 403: Prohibido, el servidor recibió la solicitud pero se niega a proporcionar el servicio.
  • 404: No encontrado, el recurso solicitado no existe; esto no hace falta decirlo.
  • 500: Error interno del servidor, se produjo un error inesperado en el servidor.
  • 503: Servidor no disponible, el servidor actualmente no puede procesar la solicitud del cliente; puede volver a la normalidad después de un tiempo.

8) Características del protocolo HTTP

Son cosas conceptuales; con saberlas basta, no hay que memorizarlas. Provienen de Baidu Baike, directamente copiadas y pegadas:

1. Admite el modelo cliente/servidor。

2. Simple y rápido: Cuando el cliente solicita un servicio al servidor, solo necesita transmitir el método de solicitud y la ruta. Los métodos de solicitud comunes son GET, HEAD y POST. Cada método especifica un tipo diferente de contacto entre el cliente y el servidor. Debido a que el protocolo HTTP es simple, el programa del servidor HTTP tiene un tamaño pequeño y, por lo tanto, la velocidad de comunicación es rápida.

3. Flexible: HTTP permite transmitir objetos de datos de cualquier tipo. El tipo que se está transmitiendo está marcado por Content-Type.

4. Sin conexión: El significado de sin conexión es limitar cada conexión a procesar solo una solicitud. Después de que el servidor procesa la solicitud del cliente y recibe la respuesta del cliente, se desconecta. Adoptar este método puede ahorrar tiempo de transmisión.

5. Sin estadoEl protocolo HTTP es un protocolo sin estado. Sin estado significa que el protocolo no tiene capacidad de memoria para el procesamiento de transacciones. La falta de estado implica que si el procesamiento posterior necesita información anterior, debe retransmitirse, lo que puede aumentar la cantidad de datos transmitidos en cada conexión. Por otro lado, cuando el servidor no necesita información previa, su respuesta es más rápida.

PD: En cuanto al modelo de siete capas OSI y al modelo de cuatro capas TCP, no se explicarán en la serie básica ~ Si te interesa, ¡puedes informarte por tu cuenta!

Resumen de esta sección:

En esta sección explicamos las herramientas que debemos completar relacionadas con la red en el desarrollo de Android, así como los conceptos relevantes del protocolo HTTP. Creo que ya tienes una idea vaga de la interacción entre el cliente móvil Android y el servidor. En la próxima sección estudiaremos las cabeceras de solicitud y de respuesta del protocolo HTTP. ¡Esto es todo por hoy, gracias!
