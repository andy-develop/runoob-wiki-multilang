Protocolo MCP

MCP (Model Context Protocol, Protocolo de Contexto de Modelo) es un protocolo abierto diseñado para lograr una integración fluida entre las aplicaciones de grandes modelos de lenguaje (LLM) y fuentes de datos, herramientas y servicios externos, de manera similar al protocolo HTTP en la red o al protocolo SMTP en el correo electrónico.

El protocolo MCP mejora la funcionalidad, flexibilidad y escalabilidad de las aplicaciones LLM al estandarizar la forma en que los modelos interactúan con recursos externos.

MCP proporciona a los desarrolladores un entorno de desarrollo unificado, eficiente e interoperable al estandarizar las reglas de comunicación en el ecosistema de aplicaciones de inteligencia artificial.

Conceptos fundamentales de MCP

El núcleo de MCP esel contexto del modelo, es decir, toda la información y herramientas externas que el LLM necesita durante su ejecución.

MCP, mediante la definición de interfaces y protocolos estandarizados, permite que el LLM acceda dinámicamente e integre lo siguiente:

  1. Fuentes de datos externas: como bases de datos, API, bibliotecas de documentos, etc., que proporcionan al LLM datos en tiempo real o históricos.
  2. Herramientas y servicios: como herramientas de cálculo, motores de búsqueda, servicios de terceros, etc., que amplían las funciones del LLM.
  3. Gestión del contexto: mantiene dinámicamente el contexto de conversación del LLM, garantizando coherencia y consistencia.

Arquitectura de MCP

La arquitectura de MCP consta de cuatro partes clave:

  1. Anfitrión (Host): El anfitrión es la aplicación de inteligencia artificial que espera obtener datos del servidor, por ejemplo, un entorno de desarrollo integrado (IDE), un chatbot, etc. El anfitrión se encarga de inicializar y gestionar los clientes, manejar la autorización de usuarios, gestionar la agregación de contexto, etc.
  2. Cliente (Client): El cliente es el puente entre el anfitrión y el servidor. Mantiene una conexión uno a uno con el servidor y se encarga del enrutamiento de mensajes, la gestión de capacidades, la negociación de protocolos y la gestión de suscripciones. El cliente garantiza que la comunicación entre el anfitrión y el servidor sea clara, segura y eficiente.
  3. Servidor (Server): El servidor es el componente que proporciona datos y herramientas externas. Ofrece contexto y funcionalidades adicionales a los grandes modelos de lenguaje mediante herramientas, recursos y plantillas de prompts. Por ejemplo, un servidor puede proporcionar llamadas a API de servicios externos como Gmail, Slack, etc.
  4. Protocolo base (Base Protocol): El protocolo base define cómo se comunican el anfitrión, el cliente y el servidor. Incluye el formato de los mensajes, la gestión del ciclo de vida y los mecanismos de transporte, entre otros.

MCP es como USB-C: permite que diferentes dispositivos se conecten entre sí mediante la misma interfaz.

Principio de funcionamiento de MCP

MCP logra la interacción entre el LLM y los recursos externos mediante la definición de formatos de datos y protocolos de comunicación estandarizados.

MCP utiliza JSON-RPC 2.0 como formato de mensaje y se comunica mediante mensajes estándar de solicitud, respuesta y notificación.

MCP admite múltiples mecanismos de transporte, incluida la entrada/salida estándar local (Stdio) y los eventos enviados por el servidor (SSE) basados en HTTP.

El ciclo de vida de MCP incluye tres fases: inicialización, ejecución y cierre, lo que garantiza que el establecimiento de la conexión, la comunicación y la terminación cumplan con las especificaciones del protocolo.

A continuación se muestra su flujo de trabajo:

1. Solicitud de contexto

La aplicación LLM envía una solicitud de contexto a los recursos externos, que incluye el tipo de datos o servicios necesarios.

  • La aplicación LLM envía solicitudes a los recursos externos según las necesidades de la tarea.
  • Los recursos externos devuelven los datos necesarios o los resultados del servicio.

2. Integración de contexto

La aplicación LLM integra los datos de contexto devueltos por los recursos externos en el modelo para generar respuestas o ejecutar tareas.

  • La aplicación LLM combina los datos externos con el conocimiento interno del modelo para generar respuestas más precisas o más completas.

3. Gestión de contexto

MCP admite la gestión dinámica del contexto de conversación del LLM, lo que garantiza la coherencia en diálogos de múltiples turnos.

  • El gestor de contexto mantiene el historial y el estado de la conversación.
  • La aplicación LLM genera respuestas coherentes basándose en el contexto.

Partes clave del protocolo: mensajes

El núcleo de MCP es el uso de JSON-RPC 2.0 como formato de mensaje, lo que proporciona una forma estandarizada de comunicación entre el cliente y el servidor.

El protocolo base define tres tipos básicos de mensajes: solicitudes (Requests), respuestas (Responses) y notificaciones (Notifications).

A continuación se ofrece una descripción detallada de estos tres tipos de mensajes:

1. Solicitudes (Requests)

Los mensajes de solicitud se utilizan para iniciar operaciones desde el cliente hacia el servidor, o desde el servidor hacia el cliente.

La estructura del mensaje de solicitud es la siguiente:

{
  "jsonrpc": "2.0",
  "id": "string | number",
  "method": "string",
  "params": {
    "[key: string]": "unknown"
  }
}
  • jsonrpc: la versión del protocolo, fijada en"2.0"。
  • id: el identificador único de la solicitud, que puede ser una cadena o un número.
  • method: el nombre del método que se va a invocar, es una cadena.
  • params: los parámetros del método, un objeto opcional de pares clave-valor, donde las claves son cadenas y los valores pueden ser de cualquier tipo.

2. Respuestas (Responses)

Los mensajes de respuesta son la contestación a una solicitud; se envían del servidor al cliente, o del cliente al servidor.

La estructura del mensaje de respuesta es la siguiente:

{
  "jsonrpc": "2.0",
  "id": "string | number",
  "result": {
    "[key: string]": "unknown"
  },
  "error": {
    "code": "number",
    "message": "string",
    "data": "unknown"
  }
}
  • jsonrpc: la versión del protocolo, fijada en"2.0"。
  • id: se corresponde con el de la solicitudidy se utiliza para identificar la solicitud a la que corresponde la respuesta.
  • result: si la solicitud tiene éxito,resultel campo contiene el resultado de la operación, que es un objeto de pares clave-valor.
  • error: si la solicitud falla,errorel campo contiene la información del error, donde:
    • code: el código de error, que es un número.
    • message: la descripción del error, que es una cadena.
    • data: información de error adicional opcional, que puede ser de cualquier tipo.

3. Notificaciones (Notifications)

Los mensajes de notificación son mensajes unidireccionales que no requieren respuesta del receptor.

La estructura del mensaje de notificación es la siguiente:

{
  "jsonrpc": "2.0",
  "method": "string",
  "params": {
    "[key: string]": "unknown"
  }
}
  • jsonrpc: la versión del protocolo, fijada en"2.0"。
  • method: el nombre del método que se va a invocar, es una cadena.
  • params: los parámetros del método, un objeto opcional de pares clave-valor, donde las claves son cadenas y los valores pueden ser de cualquier tipo.

Explicación

  • Solicitudes y respuestas: las solicitudes y las respuestas son uno a uno; después de que el cliente envía una solicitud, el servidor devuelve una respuesta.idEl campo se utiliza para asociar la solicitud y la respuesta.
  • Notificaciones: las notificaciones son unidireccionales; el emisor no necesita esperar la respuesta del receptor. Las notificaciones se utilizan normalmente en escenarios como el envío de eventos o la actualización de estados.
  • Manejo de errores: si la solicitud falla, la respuesta contendrá el campoerrorcampo, que proporciona el código y la descripción del error, ayudando a los desarrolladores a localizar rápidamente el problema.

Características clave de MCP

  1. Interfaz estandarizada: define interfaces y protocolos unificados, garantizando la compatibilidad entre el LLM y los recursos externos.
  2. Integración dinámica: admite que el LLM acceda e integre dinámicamente fuentes de datos y herramientas externas.
  3. Conciencia del contexto: admite la gestión dinámica del contexto de conversación, mejorando la coherencia de los diálogos de múltiples turnos.
  4. Apertura y extensibilidad: admite que desarrolladores externos amplíen las funciones y los recursos de las aplicaciones LLM.

Casos de uso de MCP

MCP se utiliza ampliamente en los siguientes escenarios:

  1. Sistemas de preguntas y respuestas mejorados: al integrar fuentes de datos externas, proporcionan respuestas precisas y en tiempo real.
  2. Asistentes inteligentes: al integrar herramientas y servicios, ejecutan tareas complejas (como reservas, cálculos, búsquedas, etc.).
  3. Gestión del conocimiento: al integrar bibliotecas de documentos y bases de datos, brindan apoyo de conocimiento en áreas especializadas.
  4. Diálogos de múltiples turnos: mediante la gestión del contexto, se logran diálogos coherentes de múltiples turnos.

Ventajas y desventajas de MCP

Ventajas:

  1. Ampliación de funciones: al integrar recursos externos, se amplían significativamente las funciones de las aplicaciones LLM.
  2. Flexibilidad: admite el acceso dinámico y la integración de múltiples fuentes de datos y herramientas.
  3. Apertura: el protocolo estandarizado admite el desarrollo y la integración por parte de terceros.

Desventajas:

  1. Complejidad: requiere diseñar y mantener la lógica de interacción con los recursos externos.
  2. Sobrecarga de rendimiento: el acceso a recursos externos puede introducir latencia adicional.

Alternativas a MCP

En algunos escenarios, se pueden utilizar las siguientes alternativas:

  1. API personalizada：为 LLM 应用开发自定义的 API 接口。 Desarrollar una API personalizada para aplicaciones LLM.
  2. 插件机制 Mecanismo de plugins：使用插件机制扩展 LLM 应用的功能。 Ampliar las funciones de las aplicaciones LLM mediante el mecanismo de plugins.
  3. 知识图谱 Grafo de conocimiento：通过知识图谱集成外部知识。 Integrar conocimiento externo a través de grafos de conocimiento.
