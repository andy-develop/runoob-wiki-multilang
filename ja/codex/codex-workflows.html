Codex ワークフローパターン

Codexは日常的なコーディングから複雑なリファクタリングまで、さまざまな開発ワークフローに組み込むことができ、効率を大幅に向上させます。

日常開発ワークフロー

日常開発は最も一般的なワークフローパターンで、新機能の構築や小規模な変更に適しています。

ワークフローの手順

手順操作Codexとの連携
1要件を明確にする実装したい機能を説明する
2Codexによる分析Codexがプロジェクト構造と規約を理解する
3方針の検討Codexと実装方針を確認する
4コード生成Codexがコードを作成し、ファイルを変更する
5テストで検証テストを実行して機能が正しいことを確認する
6反復的な最適化フィードバックに基づいてコードを調整する

例：新しいAPIエンドポイントの追加

日常開発の流れ

# 手順1：要件を説明する
"/api/users パスにGETエンドポイントを追加して、ユーザーリストを返す
ページネーションパラメータ page と limit をサポートする"

# 手順2-3：Codexが分析し方針を確認する
Codexは既存のAPI構造を分析し、以下を確認します：
- ルート定義の場所
- データベースクエリ方法
- レスポンス形式の規約

# 手順4：コード生成
Codexが自動的に作成：
- ルート定義
- データ取得ロジック
- エラーハンドリング
- レスポンスのフォーマット

# 手順5：テストで検証
"テストを実行し、新しいエンドポイントを確認する"

# 手順6：反復的な最適化
"キャッシュサポートを追加し、応答時間を100ms未満にする"

コード理解ワークフロー

レガシーコードや馴染みのないプロジェクトを理解する必要がある場合に、このワークフローを使用します。

探索的ワークフロー

  1. エントリーポイントから始めて、Codexに全体アーキテクチャを説明させます
  2. 主要モジュールへ段階的に掘り下げ、中核ロジックを理解します
  3. データフローと呼び出しチェーンを追跡します
  4. 重要なポイントと注意事項をまとめます

レガシープロジェクトの理解

# 全体アーキテクチャ
"このプロジェクトの全体アーキテクチャを分析し、主要モジュールとそれらの関係を説明してください"

# 中核モジュール
"src/auth モジュールの動作原理を、認証フローと権限チェックを含めて説明してください"

# データフローの追跡
"ユーザーログイン後、リクエストからレスポンスまでの完全なフローを追跡してください"

# 重要ポイントのまとめ
"このプロジェクトの中核となるデザインパターンと注意すべき点をまとめてください"

新規プロジェクトに素早く慣れる

新規プロジェクト開始ガイド

# プロジェクト概要
"これは何のプロジェクトですか？主な機能と技術スタックは何ですか？"

# 開発ガイド
"ローカルで開発環境を起動するには？テストを実行するには？"

# コーディング規約
"このプロジェクトのコーディング規約は何ですか？どんな取り決めがありますか？"

# モジュールナビゲーション
"X機能を追加する場合、どのファイルを変更すべきですか？"

リファクタリングワークフロー

リファクタリングは慎重な対応が必要ですが、Codexはコード構造を体系的に改善するのに役立ちます。

リファクタリングの原則

  • 既存のコード構造を先に理解する
  • 小さなステップでリファクタリングし、段階的に改善する
  • 各ステップで検証し、機能が変わらないことを確認する
  • テストカバレッジを維持する

リファクタリングワークフローの手順

手順説明
問題の特定Codexがコードを分析し、改善が必要な部分を特定する
方針を立てるリファクタリング方針を検討し、改善の方向性を確認する
段階的に実行小規模な変更を行い、変更のたびに検証する
テストによる検証すべてのテストを実行し、機能が正しいことを確認する
整理と最適化冗長なコードを削除し、命名を最適化する

リファクタリングの例

# 問題の特定
"src/utils モジュールを分析し、コードの重複と不合理な設計を特定してください"

# 方針を立てる
"このモジュールを後方互換性を保ちながらリファクタリングする方法を検討してください"

# 段階的に実行
"ステップ1：共通関数を utils/common.py に抽出する"

# テストによる検証
"すべてのテストを実行し、リファクタリングが機能を壊していないことを確認する"

# 次のステップへ
"ステップ2：複雑な関数を簡素化し、より小さな単位に分割する"

リファクタリング時は /plan モードで先に計画を立て、その後段階的に実行して、一度に大きな変更を加えることを避けましょう。

バグ修正ワークフロー

Codexはバグの迅速な特定と修正を支援します。

修正フロー

手順操作
問題の説明バグの症状と発生条件を説明する
情報の提供エラーメッセージ、ログ、スクリーンショットを共有する
根本原因の特定Codexが分析し根本原因を特定する
修正の生成Codexが修正案を提案する
修正の検証テストを実行して問題が解決されたことを確認する
再発防止そのシナリオをカバーするテストを追加する

バグ修正の例

# 問題の説明
"ユーザーログイン時にまれに500エラーが発生します。エラーログには次のように表示されます：
TypeError: Cannot read property 'id' of undefined"

# 情報の提供
"これは完全なエラースタックです：[スタック情報を貼り付け]"

# 根本原因の特定
Codexが分析したところ、ユーザーオブジェクトが特定の状況で null になる問題が見つかりました

# 修正の生成
"この問題を修正し、通常のログインフローに影響を与えないようにしてください"

# 修正の検証
"ログイン関連のすべてのテストを実行する"

# 再発防止
"ユーザーオブジェクトが null の場合をカバーするテストを追加する"

スクリーンショットによるデバッグ支援

スクリーンショットを使ってCodexに問題を理解させましょう：

画像入力

# CLIでスクリーンショットを添付
codex -i error-screenshot.png "このエラーを説明して修正してください"

# IDEでスクリーンショットを貼り付け
チャットにスクリーンショットを直接貼り付け、問題を説明する

コードレビューワークフロー

Codexはコードの変更をレビューし、問題を発見して改善提案を行うことができます。

レビューモード

モードトリガー方法適用シナリオ
Review ModeApp 中启用ローカルの未コミット変更をレビュー
/review コマンドCLI/IDE で使用指定範囲の変更をレビュー
GitHub 統合PR で @codex reviewPull Request をレビュー

ローカルレビュー

Review Mode

# App で Review Mode を有効にする
ツールバーの目のアイコンをクリック

# または CLI で使用
/review

# レビュー範囲を指定
/review src/auth/

# 特定のコミットをレビュー
/review HEAD~3..HEAD

レビュー重点のカスタマイズ

レビュー重点の指定

/review for security issues

# パフォーマンスレビュー

# コードスタイル

# 総合レビュー
/review --detailed

ベストプラクティス

ワークフローの選択

  • 日常開発：継続的な対話で段階的に改善
  • リファクタリング：まず計画してから実行し、小さなステップで検証
  • バグ修正：十分な情報を提供し、根本原因を検証
  • レビュー：定期的に実施し、セキュリティ問題に注目

効率化のコツ

  • AGENTS.md を使用してプロジェクト規範を定義し、重複する説明を減らす
  • Skills を利用してよく使うワークフローをカプセル化
  • Worktree を使用して異なるタスクを分離
  • 合理的な Approval ポリシーを設定

よくある質問

Q: 大規模なリファクタリングはどう扱えばよいですか？

/plan モードを使用して段階的な計画を立て、各ステップ完了後に検証します。

Q: バグ修正後、再発を防ぐにはどうすればよいですか？

そのシナリオをカバーする専用のテストを追加し、AGENTS.md に関連するチェックルールを追加します。

Q: Codexにプロジェクト規約を理解させるにはどうすればよいですか？

AGENTS.md ファイルを作成し、プロジェクトの技術スタック、コード規範、テスト要件などを定義します。

Q: レビュー結果をチームと共有するにはどうすればよいですか？

GitHub 統合を使用して PR でレビューすると、結果が自動的にコメントとして追加されます。
