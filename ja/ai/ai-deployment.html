AI エンジニアリングデプロイ

ノートPCでモデルを動かし、応答生成が速くて品質も良い状態を実現していたのに、それをサーバーにデプロイして100人のユーザーが同時に呼び出すと、状況は一変します。あるユーザーは返信を受け取るまでに10秒待たされ、あるリクエストはそのままタイムアウトエラーになり、GPU メモリはあっという間にいっぱいになります。請求額は、心が痛むほど跳ね上がります。

これが AI デプロイが解決すべき問題です。動作するモデルを、使いやすいサービスに変えることです。。

従来の Web サービスのボトルネックは通常、CPU とデータベースです。

AI サービスのボトルネックは主に GPU にあります。GPU のメモリが十分かどうか、計算が速いかどうか、同時リクエストをどうキューイングするかです。

AI デプロイの中心的な課題は、遅延、スループット、コストの3つの言葉にまとめられます。

指標意味ユーザー体感
遅延（Latency）ユーザーがリクエストを送信してから最初の文字を受け取るまでの時間速いかどうか
スループット（Throughput）1秒間に処理できるリクエスト数同時に多くの人にサービスを提供できるか
コスト（Cost）サービス運用にかかる GPU/サーバー費用高価かどうか

優れた AI デプロイとは、この3つの間でバランスを取ることです。遅延は十分低く、スループットは十分高く、コストは制御可能な状態に保ちます。

モデルサービス化フレームワーク

学習済みモデルを API サービスとしてラップするには、専用のフレームワークが必要です。この節では、vLLM、TGI、Ollama の3つの主要な選択肢を紹介します。

vLLM：PagedAttention による高性能推論

vLLM は UC Berkeley チームが開発した推論エンジンで、最大の特徴は高速であることです。

vLLM の核となる革新はPagedAttention——オペレーティングシステムの仮想メモリページングに着想を得た、GPU メモリを効率的に管理する技術です。

従来の推論フレームワークでは、各リクエストの KV Cache（キーバリューキャッシュ）が連続した GPU メモリ空間を占有する必要があります。

リクエストの長さが異なる場合、GPU メモリは断片化し、利用率が非常に低くなります。

PagedAttention は GPU メモリを固定サイズのページに分割し、各リクエストの KV Cache を異なるページに分散して保存し、ページテーブルで位置を記録します。

これにより GPU メモリの利用率が大幅に向上し、より多くのリクエストを同時に処理できます。

例

# vLLM をインストール
pip install vllm

# vLLM で OpenAI 互換の API サービスを起動
# --model でモデルを指定、--host と --port で待受アドレスを指定
# --tensor-parallel-size で並列推論に使う GPU の枚数を指定
python -m vllm.entrypoints.openai.api_server \
    --model Qwen/Qwen2.5-7B-Instruct \
    --host 0.0.0.0 \
    --port 8000 \
    --tensor-parallel-size 1 \
    --gpu-memory-utilization 0.9 \
    --max-model-len 8192

TGI：Hugging Face の推論エンジン

TGI（Text Generation Inference）は Hugging Face が提供する推論サービスフレームワークです。

その特徴は、エコシステムが充実しており、Hugging Face Hub と深く統合されていることです。Flash Attention、動的バッチ処理などの最適化をサポートします。

例

    --max-total-tokens 8192 \
    --max-batch-prefill-tokens 4096

# または Python で直接インストール（開発環境）

フレームワーク選定比較

3つのフレームワークにはそれぞれ特徴があります。どう選ぶ？あなたのニーズ次第です。

フレームワーク利点欠点適用シーン
vLLM性能最強、スループット最高設定が比較的複雑高並行本番環境、性能追求
TGIHugging Face エコシステム、デプロイ簡単性能はvLLMよりやや低いすでにHugging Faceツールチェーンを使用中
Ollama超シンプルなデプロイ、保守コストが低い超大規模な並行には不向き中小規模サービス、迅速な立ち上げ

初期段階：まずOllamaを使う。シンプルで信頼性が高い。トラフィックが増えたら：vLLMに移行。性能優先。

推論最適化技術

同じモデルでも、実行方法が異なると速度とコストが数倍変わる可能性がある。

このセクションでは本番環境でよく使われる推論最適化技術を紹介する。

連続バッチ処理（Continuous Batching）

従来のバッチ処理は静的：十分なリクエストが集まったら、まとめて推論し、すべて完了してから次のバッチを処理する。

問題は：リクエストによって短いもの（例えば10文字だけ生成）もあれば、長いもの（500文字生成）もある。

短いリクエストは長いリクエストの完了を待たなければならず、リソースをまとめて解放できないため、GPU利用率が上がらない。

連続バッチ処理は動的：リクエストが完了したら、すぐにキュー内の新しいリクエストを追加する。バッチ全体の完了を待つ必要はない。

これによりGPUはほぼ常にフル稼働し、スループットが大幅に向上する。

vLLMとTGIには連続バッチ処理が組み込まれている。手動実装は不要で、有効にするだけ。

投機的デコーディング（Speculative Decoding）

大規模モデルが1文字生成するには、完全な順伝播を1回呼び出す必要があり、遅い。

投機的サンプリングの考え方は：小さなモデルで後続の数文字を"推測"し、大規模モデルに一括で検証させる。

小さなモデルは推測が速く、必ずしも全問正解ではないが、正解した部分は一括出力できる。

間違った部分は捨てて、再び推測する。

これにより全体の速度は2〜3倍向上でき、出力品質も変わらない。

例

# vLLMで投機的サンプリングを有効にする
# --speculative-model は小さなモデル（ドラフトモデル）を指定する
# --num-speculative-tokens は毎回推測する文字数を指定する
python -m vllm.entrypoints.openai.api_server \
    --model Qwen/Qwen2.5-7B-Instruct \
    --speculative-model Qwen/Qwen2.5-0.5B-Instruct \
    --num-speculative-tokens 5 \
    --host 0.0.0.0 \
    --port 8000

量子化推論：AWQ と GPTQ

モデル量子化は、モデルの重みを16ビット浮動小数点数（FP16）から8ビットまたは4ビットの整数に圧縮すること。

VRAM使用量が半分以下になり、推論速度もさらに速くなる。

最も一般的な2つの量子化方式は AWQ と GPTQ です。

量子化方式特徴精度損失推論速度
AWQアクティベーション認識重み量子化極小快
GPTQ層ごとの最適化量子化小快
GGUFローカル実行に適する許容可能快

例

# vLLMでAWQ量子化モデルを直接実行する
# 多くの量子化モデルはHugging Faceから直接ダウンロードできる
python -m vllm.entrypoints.openai.api_server \
    --model TheBloke/Qwen2.5-7B-Instruct-AWQ \
    --quantization awq \
    --host 0.0.0.0 \
    --port 8000

# またはOllamaでGGUF量子化モデルを実行する
ollama run qwen2.5:7b-instruct-q4_0

PythonでAWQ量子化モデルをロードする：

例

# ファイルパス：awq_inference.py
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch

# AWQ量子化モデルをロード
model_name = "TheBloke/Qwen2.5-7B-Instruct-AWQ"

# 注意：実際に実行するには autoawq ライブラリのインストールが必要
# pip install autoawq

tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype=torch.float16,
    device_map="auto",
    trust_remote_code=True,
)

# 推論
messages = [
    {"role": "system", "content": "あなたは親切なAIアシスタントです。"},
    {"role": "user", "content": "runoobを紹介"}
]

text = tokenizer.apply_chat_template(
    messages,
    tokenize=False,
    add_generation_prompt=True
)

inputs = tokenizer([text], return_tensors="pt").to(model.device)

with torch.no_grad():
    outputs = model.generate(
        **inputs,
        max_new_tokens=500,
        temperature=0.7,
    )

response = tokenizer.decode(
    outputs[0][inputs.input_ids.shape[1]:],
    skip_special_tokens=True
)
print(response)

モデル蒸留

蒸留は、大規模モデル（教師）を使って小さなモデル（生徒）を訓練し、小さなモデルに大規模モデルの能力を学習させること。

小さなモデルはより速く、より安価で、効果はやや劣るが、多くのシーンで十分に使える。

例えば、Qwen2.5-72Bを教師として、Qwen2.5-7Bの生徒を訓練すると、効果は72Bに近い可能性があるが、速度とコストは7Bレベル。

蒸留の利点は通常次の通り：モデルサイズが1/10に縮小、推論速度が5〜10倍向上、効果は90%以上保持。

API サービス設計

モデルをラップするのは最初の一歩にすぎない。本番環境のAPIには認証、レート制限、ストリーミング応答、エラー処理など多くの機能が必要。

FastAPIはこれに最適な選択肢です。

# シンプルなレートリミッター（メモリ実装、本番環境ではRedisを推奨）
class RateLimiter:
    def __init__(self):
        self.requests = defaultdict(list)  # key -> [timestamp, ...]

    async def is_allowed(self, key: str, max_requests: int, window_seconds: int) -> bool:
        """レート制限を超えているかチェック"""
        now = time.time()
        # 期限切れレコードをクリーンアップ
        self.requests[key] = [t for t in self.requests[key] if now - t < window_seconds]
        # 制限超過かどうかをチェック
        if len(self.requests[key]) >= max_requests:
            return False
        # このリクエストを記録
        self.requests[key].append(now)
        return True

rate_limiter = RateLimiter()

前述の例ではシンプルなメモリ内レート制限を使用したが、本番環境ではRedisを使用した分散レート制限を推奨する。

例

# ファイルパス：redis_rate_limiter.py
import redis.asyncio as redis
import time

class RedisRateLimiter:
    """Redisベースの分散レートリミッター"""

    def __init__(self, redis_url: str = "redis://localhost:6379"):
        self.redis = redis.from_url(redis_url)

    async def is_allowed(
        self,
        key: str,
        max_requests: int,
        window_seconds: int
    ) -> bool:
        """
スライディングウィンドウレート制限アルゴリズム
key: 限流键（例：user_id や api_key）
max_requests: ウィンドウ内の最大リクエスト数
window_seconds: ウィンドウサイズ（秒）
        """
        now = time.time()
        window_start = now - window_seconds

        # Redis キー
        redis_key = f"rate_limit:{key}"

        # pipeline アトミック操作を使用
        async with self.redis.pipeline() as pipe:
            # 1. ウィンドウ外のレコードを削除
            pipe.zremrangebyscore(redis_key, 0, window_start)
            # 2. 現在のウィンドウ内のリクエスト数を集計
            pipe.zcard(redis_key)
            # 3. 現在のリクエストを追加
            pipe.zadd(redis_key, {str(now): now})
            # 4. 有効期限を設定
            pipe.expire(redis_key, window_seconds)
            # 実行
            _, current_count, _, _ = await pipe.execute()

        return current_count < max_requests

    async def close(self):
        await self.redis.close()


# 使用例
async def main():
    limiter = RedisRateLimiter("redis://localhost:6379")

    # テスト：同一ユーザーは毎分最大10回のリクエスト
    user_id = "user_123"
    for i in range(15):
        allowed = await limiter.is_allowed(user_id, max_requests=10, window_seconds=60)
        print(f"リクエスト {i+1}: {'許可' if allowed else '拒否'}")

    await limiter.close()

負荷分散とスケーリング

ユーザーが増えるにつれて、1台のサーバーでは捌ききれなくなる。マシンを追加し、トラフィックを複数台のマシンに分散させる必要がある。

これが負荷分散と自動スケーリングで解決すべき問題だ。

ステートレスサービス設計

まず覚えておくべきこと：AIサービスはステートレスに設計する。

ステートレスとは：リクエスト間でメモリを共有せず、どのサーバーがどのリクエストを処理してもよいということ。

そうすればスケールアウトは簡単だ：マシンを追加するだけでよく、データ同期を考慮する必要がない。

セッション状態（例：会話履歴）はクライアント側に保存するか（毎回ユーザーに送信してもらう）、Redisに保存すればよい。

AI モデルの A/B テスト

新バージョンのモデルをリリースしたとき、旧バージョンより優れているかどうかをどう判断するか？A/Bテストによる。

A/Bテストの核心は：トラフィックを複数のグループに分け、グループごとに異なるモデルを使い、指標を比較する。

トラフィック分割戦略

一般的なトラフィック分割方法はいくつかある：

例

# ファイルパス：ab_test_router.py
import hashlib
import random
from typing import Dict, List, Tuple
from dataclasses import dataclass

@dataclass
class Variant:
    """A/Bテストの一種"""
    name: str           # バリアント名
    model_name: str     # モデル名
    weight: int         # トラフィックの重み
    config: dict        # その他の設定


class ABTestRouter:
    """A/Bテストトラフィックルーター"""

    def __init__(self, test_name: str, variants: List[Variant]):
        self.test_name = test_name
        self.variants = variants
        # 総重みを計算
        total_weight = sum(v.weight for v in variants)
        # セグメント範囲を構築
        self.ranges: List[Tuple[int, int, Variant]] = []
        current = 0
        for v in variants:
            self.ranges.append((current, current + v.weight, v))
            current += v.weight
        self.total_weight = total_weight

    def get_variant_by_user(self, user_id: str) -> Variant:
        """
ユーザーIDに基づく安定した分割
同じユーザーは常に同じグループに割り当てられ、体験の不一致を避ける
        """
        # ハッシュでユーザーのスコアを計算
        hash_input = f"{self.test_name}-{user_id}".encode()
        hash_value = hashlib.md5(hash_input).hexdigest()
        # 0-999の数値に変換
        score = int(hash_value[:4], 16) % 1000
        # 対応するバリアントを検索
        for start, end, variant in self.ranges:
            if start <= score < end:
                return variant
        return self.variants[-1]

    def get_variant_random(self) -> Variant:
        """ランダム分割（粘着性が不要なシーン向け）"""
        score = random.randint(0, self.total_weight - 1)
        for start, end, variant in self.ranges:
            if start <= score < end:
                return variant
        return self.variants[-1]


# 使用例

指標の定義と収集

A/Bテストでは「どのモデルの応答がより賢いか」だけを見るのではなく、定量化可能な指標を定義する必要がある。

指標タイプ具体的な指標説明
システム指標レイテンシ、スループット、エラー率モデルが速いか、安定しているか
ユーザー行動ユーザー満足度、会話ターン数、継続率ユーザーが気に入っているか
ビジネス指標コンバージョン率、リテンション率、収益ビジネスに役立つか
品質指標人手評価、有害率、事実正確性出力品質が良いか

統計的有意性の判断

データを取得した後、A群52%、B群55%だからといって、単純にB群の方が良いとは言えない。

統計的有意性検定を行い、差異がランダムな変動によるものではないことを確認する必要がある。

例

# ファイルパス：ab_test_analysis.py
import math
from typing import Tuple

def calculate_z_test(
    control_conv: float,
    treatment_conv: float,
    control_total: int,
    treatment_total: int
) -> Tuple[float, float]:
    """
Z検定のp値を計算
control_conv: 対照群のコンバージョン率
treatment_conv: 実験群のコンバージョン率
control_total: 対照群のサンプル数
treatment_total: 実験群のサンプル数
    """
    # プールされたコンバージョン率
    p_pool = (control_conv * control_total + treatment_conv * treatment_total) / (control_total + treatment_total)
    # 標準誤差
    se_pool = math.sqrt(p_pool * (1 - p_pool) * (1 / control_total + 1 / treatment_total))
    # Z統計量
    z_score = (treatment_conv - control_conv) / se_pool
    # p値を計算（両側検定）
    p_value = 2 * (1 - normal_cdf(abs(z_score)))
    return z_score, p_value

def normal_cdf(x: float) -> float:
    """標準正規分布の累積分布関数（近似）"""
    return (1.0 + math.erf(x / math.sqrt(2.0))) / 2.0

def analyze_ab_test(
    control_conversions: int,
    control_total: int,
    treatment_conversions: int,
    treatment_total: int,
    alpha: float = 0.05
):
    """A/Bテスト結果の分析"""
    control_conv = control_conversions / control_total
    treatment_conv = treatment_conversions / treatment_total

    z_score, p_value = calculate_z_test(
        control_conv, treatment_conv,
        control_total, treatment_total
    )

    relative_lift = (treatment_conv - control_conv) / control_conv

    print("A/Bテスト結果の分析")
    print("=" * 50)
    print(f"対照群: {control_conversions}/{control_total} ({control_conv:.2%})")
    print(f"実験群: {treatment_conversions}/{treatment_total} ({treatment_conv:.2%})")
    print(f"相対リフト: {relative_lift:+.2%}")
    print("-" * 50)
    print(f"Z統計量: {z_score:.4f}")
    print(f"p-value: {p_value:.4f}")
    print("-" * 50)

    if p_value < alpha:
        print(f"&#x2705; 結果は統計的に有意（p < {alpha}）")
        if relative_lift > 0:
            print(" 実験群の方が優れています！")
        else:
            print(" 対照群の方が優れています！")
    else:
        print(f"&#x274c; 結果は有意ではない（p >= {alpha}）")
        print(" どちらのバージョンが良いか判断できないため、より多くのデータが必要です")

監視とアラート

サービスが稼働を開始しましたが、正常に動作しているかどうかはどうやってわかりますか？ユーザーはタイムアウトに遭遇するでしょうか？モデルはどんどん不正確になるでしょうか？

完全な監視システムが必要です。

主要指標：TTFT、TPS、エラー率

AIサービスにはいくつかのコア監視メトリクスがあります：

メトリクス正式名称意味アラートしきい値の例
TTFTTime to First Tokenユーザーがリクエストを送信してから最初の文字を受信するまでの時間> 3 秒でアラート
TPOTTime per Output Token各出力トークンの平均所要時間> 100ms でアラート
TPSTokens Per Second1秒あたりに生成されるトークン数< 100 でアラート
エラー率Error Rate失敗したリクエストの割合> 5% でアラート
GPU使用率GPU UtilizationGPU使用率< 30% または > 95% でアラート
GPUメモリ使用量GPU MemoryGPUメモリ使用率> 90% でアラート

AI 特有の監視：ドリフト検出

AI モデルは「壊れる」だけでなく、「ドリフト」もします。時間の経過とともにデータ分布が変わり、モデルの性能が低下します。

例

# ファイルパス: drift_detection.py
import numpy as np
from scipy import stats
from dataclasses import dataclass
from typing import List, Tuple
import json

@dataclass
class DistributionStats:
    """分布統計情報"""
    mean: float
    std: float
    min: float
    max: float
    percentiles: dict


class DataDriftDetector:
    """データドリフト検出器"""

    def __init__(self, baseline_data: np.ndarray):
        """ベースラインデータで初期化する"""
        self.baseline_stats = self._compute_stats(baseline_data)
        self.baseline_data = baseline_data

    def _compute_stats(self, data: np.ndarray) -> DistributionStats:
        """データの統計情報を計算する"""
        return DistributionStats(
            mean=float(np.mean(data)),
            std=float(np.std(data)),
            min=float(np.min(data)),
            max=float(np.max(data)),
            percentiles={
                "p10": float(np.percentile(data, 10)),
                "p25": float(np.percentile(data, 25)),
                "p50": float(np.percentile(data, 50)),
                "p75": float(np.percentile(data, 75)),
                "p90": float(np.percentile(data, 90))
            }
        )

    def detect(self, new_data: np.ndarray, threshold: float = 0.05) -> dict:
        """
ドリフトを検出
戻り値: ドリフトがあるかどうか、p値、統計情報
        """
        # KS 検定: 2つの分布が同じかどうかを比較
        ks_statistic, ks_pvalue = stats.ks_2samp(self.baseline_data, new_data)

        # 新しいデータの統計を計算
        new_stats = self._compute_stats(new_data)

        # 平均値の差（パーセント）を計算
        mean_diff_pct = abs((new_stats.mean - self.baseline_stats.mean) / self.baseline_stats.mean * 100)

        # ドリフトかどうかを判定
        is_drift = ks_pvalue < threshold

        return {
            "is_drift": is_drift,
            "ks_statistic": float(ks_statistic),
            "ks_pvalue": float(ks_pvalue),
            "mean_diff_percent": float(mean_diff_pct),
            "baseline_stats": self.baseline_stats,
            "new_stats": new_stats,
            "threshold": threshold
        }

リクエストキャッシュ：セマンティックキャッシュ

従来のキャッシュは完全一致です。まったく同じ質問には、以前の回答を直接返します。

セマンティックキャッシュはさらに進んで、類似した質問でも以前の回答や中間結果を再利用できます。

例

# ファイルパス: semantic_cache.py
import numpy as np
from typing import Optional, Tuple
import time

class SemanticCache:
    """シンプルなセマンティックキャッシュ実装"""

    def __init__(self, threshold: float = 0.9):
        self.threshold = threshold
        self.queries = []  # 質問のベクトルを保存
        self.answers = []  # 対応する回答を保存
        self.timestamps = []  # 時間を保存

    def _simulate_embedding(self, text: str) -> np.ndarray:
        """
embedding をシミュレートします。実際のプロジェクトでは OpenAI Embeddings、Sentence-Transformers などを使用します。
        """
        # シンプルなハッシュシミュレーション。実際のプロジェクトでは実際の embedding モデルを使用
        np.random.seed(hash(text) % (2**32))
        return np.random.randn(128)  # 128次元ベクトル

    def _cosine_similarity(self, a: np.ndarray, b: np.ndarray) -> float:
        """コサイン類似度を計算"""
        return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

    def get(self, query: str) -> Optional[str]:
        """キャッシュを照会し、類似した質問が見つかったら回答を返す"""
        query_vec = self._simulate_embedding(query)

        for i, (q_vec, answer, ts) in enumerate(zip(self.queries, self.answers, self.timestamps)):
            # 有効期限のクリーンアップ（1時間超）
            if time.time() - ts > 3600:
                continue

            similarity = self._cosine_similarity(query_vec, q_vec)
            if similarity >= self.threshold:
                return answer

        return None

    def put(self, query: str, answer: str):
        """キャッシュに保存"""
        query_vec = self._simulate_embedding(query)
        self.queries.append(query_vec)
        self.answers.append(answer)
        self.timestamps.append(time.time())

        # シンプルな容量制御: 最大1000件保存
        if len(self.queries) > 1000:
            self.queries = self.queries[-1000:]
            self.answers = self.answers[-1000:]
            self.timestamps = self.timestamps[-1000:]


# 使用例
def main():
    cache = SemanticCache(threshold=0.9)

    # 最初のリクエスト
    query1 = "Python で CSV ファイルを読み取る方法は？"
    print(f"クエリ 1: {query1}")
    answer1 = cache.get(query1)
    if answer1:
        print(f"キャッシュヒット: {answer1}")
    else:
        print("キャッシュミス、モデルを呼び出し...")
        answer1 = "pandas.read_csv('file.csv') で CSV ファイルを読み取れます。"
        cache.put(query1, answer1)
        print(f"キャッシュに保存: {answer1}")

    print()

    # 2回目: 類似した質問
    query2 = "Python で CSV をどう読む？"
    print(f"クエリ 2: {query2}")
    answer2 = cache.get(query2)
    if answer2:
        print(f"キャッシュヒット: {answer2}")
    else:
        print("キャッシュミス、モデルを呼び出し...")

すべてのリクエストに大規模モデルが必要なわけではありません。簡単な質問は小規模モデル、複雑な質問は大規模モデルを使用します。

from dataclasses import dataclass

class SmartModelRouter:
    """スマートモデルルーター"""

    def __init__(self):
        self.models = {
            "small": ModelConfig(
                name="Qwen2.5-0.5B-Instruct",
                cost_per_1k_tokens=0.001,
                max_tokens=4096,
                capabilities=["chat", "simple_qa", "summarization"]
            ),
            "medium": ModelConfig(
                name="Qwen2.5-7B-Instruct",
                cost_per_1k_tokens=0.01,
                max_tokens=8192,
                capabilities=["chat", "qa", "coding", "reasoning"]
            ),
            "large": ModelConfig(
                name="Qwen2.5-72B-Instruct",
                cost_per_1k_tokens=0.1,
                max_tokens=32768,
                capabilities=["complex_qa", "advanced_coding", "deep_reasoning"]
            )
        }

    def _classify_query(self, query: str) -> str:
        """
簡単な質問分類（実際のプロジェクトでは分類器を使用可能）
戻り値: small/medium/large
        """
        query_lower = query.lower()

        # 簡単な質問のキーワード
        simple_keywords = [
            "こんにちは", "hello", "ありがとう", "hi", "さようなら",
            "今日の天気", "何時", "日付",
            "翻訳を手伝う", "translate",
            "簡単な紹介", "とは"
        ]

        # 複雑な質問のキーワード
        complex_keywords = [
            "コード", "書く", "実装", "code", "python",
            "分析", "理由を説明", "導出", "証明",
            "比較", "対比", "違い",
            "詳細", "深い", "複雑"
        ]

        # 簡単な質問かどうかを確認
        for keyword in simple_keywords:
            if keyword in query_lower:
                return "small"

        # 複雑な質問かどうかを確認
        for keyword in complex_keywords:
            if keyword in query_lower:
                return "large"

        # デフォルトは中規模モデル
        return "medium"

    def route(self, query: str, user_tier: str = "free") -> str:
        """
ルーティング決定
        """
        # まず質問を分類
        category = self._classify_query(query)

        # 有料ユーザーはより良いモデルを使用可能
        if user_tier == "pro":
            upgrade_map = {
                "small": "small",
                "medium": "medium",
                "large": "large"
            }
            category = upgrade_map[category]
        elif user_tier == "enterprise":
            upgrade_map = {
                "small": "medium",
                "medium": "large",
                "large": "large"
            }
            category = upgrade_map.get(category, category)

        # モデル名を返す
        return self.models[category].name

    def get_cost_estimate(self, model_name: str, input_tokens: int, output_tokens: int) -> float:
        """コストを見積もる"""
        for model in self.models.values():
            if model.name == model_name:
                return (input_tokens + output_tokens) * model.cost_per_1k_tokens / 1000
        return 0.0

障害処理とデグレード

本番環境に「障害が起きない」はありません。あるのは「障害時にどう優雅に対応するか」だけです。

デグレード戦略

例

# ファイルパス: fallback_handler.py
import time
from typing import Optional
from dataclasses import dataclass
from enum import Enum

class ServiceStatus(Enum):
    HEALTHY = "healthy"
    DEGRADED = "degraded"
    FAILED = "failed"

@dataclass
class FallbackResponse:
    content: str
    is_fallback: bool
    fallback_reason: Optional[str] = None


class FallbackHandler:
    """フォールバックハンドラー"""

    def __init__(self):
        self.error_count = 0
        self.last_error_time = 0
        self.circuit_open = False
        self.circuit_open_time = 0

        # サーキットブレーカー設定
        self.error_threshold = 5  # 連続5回エラーでサーキットブレーカーが作動
        self.circuit_timeout = 30  # サーキットブレーカー作動から30秒後に復旧を試みる

    def _call_primary_service(self, query: str) -> str:
        """メインサービスの呼び出しをシミュレート"""
        # ここを実際のモデル呼び出しに置き換える
        return "これはメインサービスの返信です"

    def _call_fallback_service(self, query: str) -> str:
        """フォールバックサービスの呼び出しをシミュレート（高速だが品質はやや低い）"""
        # より小さいモデル、キャッシュされた応答、さらにはプリセットテンプレートでもよい
        return "申し訳ございません。サービスが一時的に混雑しています。これは簡略化された応答です。"

    def _call_static_fallback(self, query: str) -> str:
        """静的フォールバック応答（最後の防衛ライン）"""
        return (
            "大変申し訳ございませんが、現在サービスに問題が発生しています。\n"
            "しばらくしてからもう一度お試しください。緊急の問題は support@runoob.com までご連絡ください。"
        )

    def process_request(self, query: str) -> FallbackResponse:
        """完全なフォールバックロジックを備えたリクエスト処理"""

        # 1. サーキットブレーカーが開いているか確認
        if self.circuit_open:
            if time.time() - self.circuit_open_time > self.circuit_timeout:
                # タイムアウトしたため、ハーフオープン状態を試行し、少量のリクエストを許可
                print("サーキットブレーカーがハーフオープン、復旧を試行中...")
                self.circuit_open = False
            else:
                # 直接フォールバック
                print("サーキットブレーカーがオープン、直接フォールバック")
                return FallbackResponse(
                    content=self._call_fallback_service(query),
                    is_fallback=True,
                    fallback_reason="circuit_open"
                )

        # 2. メインサービスを試行
        try:
            result = self._call_primary_service(query)
            # 成功：エラーカウントをリセット
            self.error_count = 0
            return FallbackResponse(
                content=result,
                is_fallback=False
            )

        except Exception as e:
            print(f"メインサービスの呼び出しに失敗: {e}")
            self.error_count += 1
            self.last_error_time = time.time()

            # 3. サーキットブレーカーが必要かどうか確認
            if self.error_count >= self.error_threshold:
                print("エラー回数が多すぎるため、サーキットブレーカーをオープン")
                self.circuit_open = True
                self.circuit_open_time = time.time()

            # 4. フォールバックサービスを試行
            try:
                print("フォールバックサービスの呼び出しを試行")
                result = self._call_fallback_service(query)
                return FallbackResponse(
                    content=result,
                    is_fallback=True,
                    fallback_reason="primary_failed"
                )
            except Exception as e2:
                print(f"フォールバックサービスも失敗: {e2}")

                # 5. 最後の静的応答
                return FallbackResponse(
                    content=self._call_static_fallback(query),
                    is_fallback=True,
                    fallback_reason="all_failed"
                )
