0.3 Verilog コード規範

カテゴリ Verilog チュートリアル上級編

ふと数年前に自分が書いた FPGA 設計を見かけたが、コードスタイルはなんとか許容範囲だったものの、論理設計面での安全上の問題が至る所にあった。多くの初心者が Verilog コードを書くとき、基本的に C 言語の思考やスタイルに従って設計しており、多くの不規範な共通問題を引き起こしている。

本節では、主に不規範で危険な Verilog 設計についてまとめる。主に合成可能なデジタル設計を対象としており、testbench はシミュレーションプログラムであるため、通常はそれほど厳しい要件はない。

コード規範で述べる内容は、コーディングスタイルとは異なる。コーディングスタイルは単なる提案であり、設計者は本チュートリアルのコーディングスタイルの提案に従わず、思いのままにコードを書いてもよい。論理が正しく、回路が安全であれば、たとえ柳絮が舞い散るような乱雑なスタイルでも、コンパイラが正常にコンパイル・シミュレーションできればよい。設計者は誇らしげに「自分のコードは自分流に書く、他人に推測させるがいい」と言えるだろう。

コード規範は、ある程度は必ず従わなければならないルールである。そうでなければ、デジタル回路論理の正確性に一定の影響を与える可能性がある。特殊な設計を目的とする場合や、個人が熟知しており十分な自信がある場合は、Verilog コード規範を多少逸脱してもよいが、それ以外の場合は設計においてこれらの規範に十分注意することを推奨する。特に初心者はこのような問題を犯しやすい。

初期値代入について

変数宣言時に変数へ初期値を代入する操作をしてはならない。変数宣言時に初期値を設定すると、シミュレーション時には変数は期待どおりの初期値を持つが、合成後の回路の初期値は不確定である。信号の初期値が論理機能に影響を与える場合、シミュレーション過程で検証が不十分なため、論理エラーを見つける機会を逃す可能性がある。例えば、以下の記述は推奨されない：

    reg [31:0]      wdata = 32'b0 ;

初期値代入操作はリセット状態で行うべきである。また、レジスタ変数にはすべてリセット端子を使用することを推奨する。これにより、システムの電源投入時や動作が乱れたときに、リセット操作でシステムを初期状態に戻すことができる。

設計時には、クロックは立ち上がりエッジ論理、リセットは立ち下がりエッジ論理を採用することを推奨する。リセット設計の詳細は『5.1 リセット入門』。

リセット時には、ステートメントブロック内のすべての信号に初期値を代入しなければならず、関連する信号を漏らしてはならない。

    always @(posedge clk or negedge rstn) begin
        if (!rstn) begin
            cnt  <= 'b0 ; //cout への初期値代入を漏らしているのは危険
        end
        else if (cnt == 10) begin
            cnt  <= 4'b0 ;
            cout <= 1'b1 ;
        end
        else begin
            cnt  <= cnt + 1'b1 ;
            cout <= 1'b0 ;
        end
    end

always 文について

やむを得ない場合を除き、2 つの always ブロックでそれぞれ同じクロックの立ち上がりエッジと立ち下がりエッジの論理を使用すべきではない。そうしないと、比較的複雑なクロック品質とタイミング制約の問題が生じる。

   //2 つの always ブロックで 2 つのクロックエッジの論理を使用することは避けたほうがよい
   always @(posedge clk) begin
      a <= b ;
   end
   always @(negedge clk) begin
      c <= d ;
   end

1 つの always ブロック内でクロックの両エッジを同時にトリガ条件として使用することは禁止する。コンパイルやシミュレーションは設計者の意図どおりに行われる可能性があるが、このような回路は多くの場合、合成できないか、合成後の回路機能が期待どおりにならない。

   //1 つの always ブロックでの両エッジ論理の使用は禁止
   always @(posedge clk or negedge clk) begin
      a <= b ;
   end  

2 つの always ブロックで同じ変数に値を代入することは禁止する。これは多くの初心者が犯しやすい誤りである。

  //この設計は誤りである
   always @(posedge clk) begin
      a <= b ;
   end
   always @(negedge clk) begin
      a <= d ;
   end

1 つの always ブロック内に複数の並行する、または無関係な条件文を存在させてはならない。複数の always を使用してそれぞれ記述すること。

1 つの always 文内に複数の並行する、または無関係な条件文が存在する場合、シミュレーションの実行結果や合成後の実際の回路では、無関係な条件文はすべて並行して実行される。しかし、シミュレーション過程は順次実行される可能性があり、遅延情報がある場合は予測できない誤った結果を引き起こす可能性がある。また、この書き方は可読性が低く、機能構造の区分が明確ではない。

    //推奨しない
    always @(posedge clk) begin
        if (a == b)
            data_t1 <= data1 ;

        if (a == b && c == d)
            data_t2 <= data2 ;
        else
            data_t2 <= 'b0 ;
    end
   
    //分けて記述することを推奨
    always @(posedge clk) begin
        if (a == b)
            data_t1 <= data1 ;
    end
    always @(posedge clk) begin
        if (a == b && c == d)
            data_t2 <= data2 ;
        else
            data_t2 <= 'b0
    end

クロックと非同期について

設計ではできるだけ同期設計を使用すること。

非同期論理をどうしても使用しなければならない場合は、異なるクロックドメイン間の信号を必ず同期処理しなければならず、関連する信号を直接使用してはならない。そうしないと、メタステーブル回路が発生する。同期処理の具体的な実装は次を参照のこと：『4.1 同期と非同期』およびその後の関連する章。

クロック信号と通常の変数信号を直接論理演算することや、クロック信号に対してレベル信号の検出・判定を行うことはできるだけ避けること。例えば、以下の記述はすべて推奨されない。

    assign clk_gate = clk & clken ;
    assign dout = (clk == 1'b1) ? din : 0 ;
    always @(posedge clk) begin
        if (clk = 1'b1)
            data_t1 <= data1 ;
    end    

異なる条件下でクロックを選択する場合、選択論理を直接使用してはならない。そうしないと、グリッチ現象が発生する。詳細は『5.4 クロック切替』。

合成について

一般的に、信号変数では乗算を直接使用してはならない*、除算/、剰余演算%などの操作。これらの演算子は合成後、構造とタイミングを制御しにくいことが多い。最適化された関連 IP モジュールやプロセスライブラリ内の集積モジュールを使用すべきである。ただし、parameter 型の定数ではこのような演算子を使用してもよい。コンパイルの初期段階でコンパイラが定数演算の結果を計算するため、余分なハードウェアリソースを消費しない。

組み合わせ論理の条件文では条件を完全に補完し、組み合わせ論理の always 文ではセンシティブ信号を漏れなく列挙して、意図しないラッチ（Latch）の発生を避けること。詳細は『Verilog チュートリアル』の章『6.5 Verilog で Latch を回避する』。

論理設計時には、コードが実際の回路に合成できるかどうか、どのような回路に合成されるかを考慮すること。詳細は『9.2 合成可能な設計』。

インスタンス化について

インスタンス化時、入力端に接続する信号は reg 型または wire 型の変数でよいが、出力端に接続する信号は必ず wire 型の変数でなければならない。ただし、ポート信号の宣言時、入力信号は wire 型変数でなければならず、出力信号は reg 型または wire 型の変数でよい。

複数のモジュールをインスタンス化する場合、モジュール名を前に、インスタンス化名を後ろに置く。また、インスタンス化名は同じであってはならない。
