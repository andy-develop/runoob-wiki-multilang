AndroidアプリにおけるOOM問題の分析と解決策

カテゴリ プログラミング技術

1. OOMとは何か？

03-21 21:05:28.771: E/dalvikvm-heap(13316): Out of memory on a 10485776-byte allocation.
03-21 21:05:28.779: E/AndroidRuntime(13316): java.lang.OutOfMemoryError

これらの記述の意味は、我々のプログラムが10485776byteのメモリを申請するには大きすぎるため、仮想マシンがそれに応えられず、恥ずかしながらシャットダウンして自殺してしまうということです。この現象は通常、多くの画像や非常に大きな画像を使用するAPP開発で発生します。簡単に言うと、APPが画像を格納するためにメモリを申請する必要があるとき、システムは我々のAPPが使用しているメモリがすでに十分多いと判断します。たとえシステムに1Gの空きメモリがあっても、APPにより多くのメモリを割り当てることを認めません。そしてシステムがすぐにOOMエラーをスローしても、プログラムがそのエラーをキャッチしなければ、ダイアログが表示されてクラッシュします。

2. なぜOOMが発生するのか？

Androidシステムのアプリの各プロセスまたは各仮想マシンには最大メモリ制限があるため、申請したメモリリソースがこの制限を超えると、システムはOOMエラーをスローします。デバイス全体の残りメモリとはあまり関係ありません。例えば、比較的古いAndroidシステムの仮想マシンは最大16Mメモリです。アプリが起動すると、仮想マシンは画像を読み込むためにメモリリソースを絶えず申請し、メモリ上限を超えるとOOMが発生します。AndroidシステムのAPPメモリ制限はどのように決定されるのでしょうか？

2.1 AndroidのAPPメモリの構成：

APPメモリは、dalvikメモリ 和 nativeメモリの2つの部分から構成されます。dalvikはすなわちJavaヒープであり、生成されたオブジェクトはここで割り当てられます。nativeはc/c++方式でメモリを申請するものであり、Bitmapはこの方式で割り当てられます。（Android 3.0以降、システムはデフォルトでdalvikを通じて割り当て、nativeはヒープとして管理されます）。この2つの部分の合計は、Androidの単一プロセス、仮想マシンに対するメモリ制限を超えてはなりません。

各スマートフォンのメモリ制限の大きさはどれくらいですか？

ActivityManager activityManager = (ActivityManager)context.getSystemService(Context.ACTIVITY_SERVICE)
activityManager.getMemoryClass();

上記の方法はM単位の数値を返します。異なるシステムプラットフォームやデバイスでは値が異なります。例えば、HTCはデフォルトで24M、Galaxyは36M、emulator-2.3は24Mなどです。私のmoto xt681は42Mです。

上記で取得したのは仮想マシンの最大メモリリソースです。

一方、headヒープのサイズ制限については、/system/build.propファイルを確認できます。

dalvik.vm.heapstartsize  =  5m
dalvik.vm.heapgrowthlimit = 48m
dalvik.vm.heapsize = 256m

注：heapsizeパラメータは単一プロセスのヒープが使用可能な最大メモリを示しますが、以下のパラメータ"dalvik.vm.headgrowthlimit =48m"が存在する場合、単一プロセスのヒープメモリが48mに制限されることを意味し、つまりプログラム実行中は実際に48mのメモリしか使用できません。

2.2 なぜAndroidシステムはAPPのメモリ制限を設定するのか？

1   開発者のメモリ使用をより合理的にするためです。各アプリケーションの利用可能なメモリ上限を制限することで、一部のアプリケーションが悪意を持って、または意図せずに過剰なメモリを使用することを防ぎ、その結果他のアプリケーションが正常に動作できなくなることを防ぎます。Androidはマルチプロセスであり、あるプロセス（つまり1つのアプリケーション）が過剰なメモリを消費すると、他のアプリケーションが実行できなくなります。制限があるため、開発者は限られたリソースをしっかり活用し、リソースの使用を最適化しなければなりません。

2 画面に表示できる内容は限られており、メモリが十分であればよいのです。たとえ数多くの画像や千万ものデータを使用する必要があっても、特定の瞬間にユーザーに見せる必要があるものは常に限られています。なぜなら画面の表示領域はその程度の大きさであり、そこに配置できる情報は非常に限られているからです。ほとんどの情報は表示準備状態にあり、そのためあまり多くのヒープメモリを与える必要はありません。つまり、OOM現象が発生する場合、その大部分の原因は我々のプログラム設計に問題があり、最適化が必要であるということです。OOM現象は、大部分は我々のプログラム設計に問題があり、最適化が必要です。最適化方法は多くあります。例えば、時間を空間に換算し、使用する画像を絶えず読み込み、不要な画像を絶えず回収し、大きな画像をスマートフォンの画面サイズに適した画像に解析するなどです。

3   複数のAPP、複数の仮想マシンdavlikの制限が必要だからです。Android上のアプリは独立した仮想マシンを使用し、アプリを開くたびに少なくとも1つの独立した仮想マシンが起動されます。これにより、仮想マシンのクラッシュがシステム全体のクラッシュを引き起こすことを防げますが、その代償としてより多くのメモリを浪費する必要があります。この設計によりAndroidの安定性が保証されています。

2.3 GCが自動的にリソースを回収してくれるのではないのか、なぜOOMが発生するのか？

AndroidのGCは自動的にリソースを回収してくれるのではないのか、なぜアプリの不要なリソースを回収しないのか？

Androidのgcは特定のアルゴリズムに従って、プログラムが不要になったメモリリソースを回収し、アプリのメモリ申請が徐々に増えていくのを防ぎます。しかし、gcが一般的に回収するリソースは、無主（参照されていない）オブジェクトのメモリやソフト参照のリソース、またはよりソフトな参照のリソースです。例えば：

Bitmap bt = BitmapFactory.decodeResource( this .getResources(), R.drawable.splash);  //此时的图片资源是强引用，是有主的资源。
bt ＝  null ;  //此时这个图片资源就是无主的了。gc心情号的时候就会去回收它。
SoftReference<Bitmap> softRef =  new  SoftReference<Bitmap>(bt);
bt =  null ;
其他代码...

プログラムが多くのメモリリソースを申請するとき、gcはsoftrefが参照するこの画像メモリを解放する可能性があります。bt＝softRef.get()とした場合、このときnullが返される可能性があり、画像を再読み込みする必要があります。

もちろん、これは画像リソースにソフト参照を使用する利点も示しています。gcが必要に応じて自動的にリソースを解放し、ある程度OOMを回避できるからです。

TIPS: プログラミングでは、不要なオブジェクトをnullに設定する習慣を身につけましょう。実際には、不要な画像は直接recycleする方が良いです。なぜなら、nullに設定してgcに回収させる場合、間に合わないことがあるからです。

2.4 APPのメモリ割り当て状況を確認する方法は？

1. DDMSのheapタブを通じてメモリ状況を監視する：

Heapビューの中央にdata objectというものがあります。つまりデータオブジェクトであり、我々のプログラム内に大量に存在するクラス型オブジェクトのことです。

data objectの行に"Total Size"という列があり、その値は現在のプロセス内のすべてのJavaデータオブジェクトのメモリ総量です。コード内にオブジェクト参照を解放していない状況が存在する場合、data objectの"Total Size"の値は毎回のgc後も明確な減少が見られません。操作回数の増加に伴い"Total Size"の値はますます大きくなります。上限に達するとプロセスがkillされます。

2. App内ではtotalMemoryとfreeMemoryを使用して確認できます： 

Runtime.getRuntime().freeMemory()
RUntime.getRuntime().totalMemory()

3  adb shell dumpsys meminfo com.android.demo

3. OOMを回避するための一般的な注意点：

3.1 画像サイズを適切に調整する。スマートフォンの画面サイズは限られており、画像に割り当てられる表示領域も限られています。特に超大画像の場合、ネットワークやSDカードから読み込む際、画像ファイルのサイズが数Mまたは十数Mに達することがあります：

メモリに読み込む前に、まずそのbitmapのサイズを計算し、サンプリングレートを適切に調整することで、読み込む画像がちょうど良いか、またはスマートフォンの画面に表示するのに少し大きい程度にします：

BimtapFactory.Option opts =  new   BitampFactory.Option();
        opts.inJustDecodeBounds =  true ;
        opts.inSampleSize=computeSample(opts, minSideLength, maxNumOfPixels);  // Android 提供了一种动态计算的方法 computeSampleSize
        opts.inJustDecodeBounds =  false ;
         try {
                return  BitmapFactory.decodeFile(imageFile, opts);
        }  catch (OutOfMemoryError err){
}

3.2 画像キャッシュ。listviewやGalleryなどのコントロールで一度に大量の画像を読み込む場合、画面に表示されるリソースのみを読み込み、まだ表示されていないものは読み込まず、画面外に移動したリソースはすぐに解放します。強参照＋ソフト参照の2段階キャッシュを採用して、読み込み性能を向上させます。画像をメモリにキャッシュする際、ソフト参照を使用してメモリにキャッシュし、使用のたびに毎回メモリに再読み込みするのではなく、キャッシュから取得します。

3.3 メモリ使用量が少ないエンコード方式を採用する。例えば、Bitmap.Config.ARGB_4444はBitmap.Config.ARGB_8888よりメモリを節約できます。

3.4 画像をすぐに回収する。大量のBitmapオブジェクトを参照しているが、アプリケーションがすべての画像を同時に表示する必要がない場合、一時的に不要なBitmapオブジェクトをすぐに回収できます。画像の使用状況が明確にわかるシナリオでは、積極的にrecycleして回収できます。

App起動時のsplash画面の画像リソースは、使用後すぐにrecycleします。フレームアニメーションの場合、1枚読み込んで、1枚描画し、1枚解放する方式が取れます。

3.5 ループ内でローカル変数を過剰に生成しない。staticの使用には注意が必要です。staticを使用してメンバー変数を修飾する場合、その変数はクラスのインスタンスではなくクラスに属し、そのライフサイクルは非常に長くなります。これを使用してメモリ使用量が多いインスタンスを参照する場合は、慎重に対処する必要があります。

3.6 ヒープメモリの割り当てサイズをカスタマイズする。Dalvik仮想マシンのヒープメモリ割り当てを最適化します。

public   class  ClassName{
    private   static  Context mContext;
       // 省略
}

4. Appが画像を使用する際にOOMを回避するいくつかの方法：

4.1  直接nullまたはrecycleする

アプリ内で使用される大量の画像に対して、以下の方法を採用します：使用時に読み込み、表示しない場合は直接nullまたはrecycleします。

このように処理するのは良い習慣であり、基本的にOOMを防げますが、欠点はコードが増え、一部のリソースのrecycleを忘れる可能性があることです。

また、特定の画像が繰り返し読み込み、解放、再読み込みされる状況が発生し、非効率的になる場合もあります。

4.2 SoftReference参照方式で画像リソースを簡単に管理する

SoftReferenceのhashmapを作成します。

画像を使用する際、まずこのhashmapにsoftreferenceがあるかどうか、softreference内の画像が空でないかを確認します。

空であれば、画像をsoftreferenceに読み込んでhashmapに追加します。

コード内で画像の回収と解放を明示的に処理する必要はなく、gcが自動的にリソースの解放を処理します。

この方法は処理が簡単で実用的であり、前の方法のように繰り返しロードと解放を行う非効率さをある程度回避できます。しかし、まだ十分に最適化されていません。

4.3 強参照＋ソフト参照の2段階キャッシュ

AndroidのサンプルプログラムImageDownloader.javaは、2段階キャッシュメカニズムを使用しています。デコードに成功したBitmapオブジェクトの参照を直接保持するデータ構造があり、同時に2段階目のキャッシュデータ構造を使用して、淘汰されたBitmapのsoftreferenceオブジェクトを保持します。softreferenceオブジェクトの特殊性により、システムはメモリが必要なときにまずsoftreferenceが保持するオブジェクトを解放します。つまり、VMが利用可能なメモリが少なくGCを実行する必要があると判断したとき、2段階キャッシュ内のbitmapオブジェクトは回収され、1段階キャッシュが保持するbitmapオブジェクトは表示に使用されます。

実際、このソリューションの最も重要なポイントは、適切なデータ構造を使用していることです。それはLinkedHashMap型を1段階キャッシュのBitmapコンテナとして使用することです。LinkeHashMapの特殊性により、メモリ内に格納するオブジェクトの数を制御でき、使用されなくなったオブジェクトをコンテナから削除して、softreferenceの2段階キャッシュに入れることができます。1段階キャッシュには最近アクセスされたbitmapオブジェクトを常に保存でき、LinkedHashMapの容量が設定値を超えると、コンテナ内で最も長く存在しているオブジェクトが削除されます。このとき、削除されたLinkedHashMap内のオブジェクトを2段階キャッシュコンテナに入れることができ、2段階キャッシュ内のオブジェクト管理はシステムに任せます。システムがGCを実行する必要があるとき、まず2段階キャッシュコンテナのBitmapオブジェクトが回収されます。

画像オブジェクトを取得するときは、まず1段階キャッシュコンテナから検索します。対応するオブジェクトがあり利用可能であれば直接返します。ない場合は、2段階キャッシュから対応するSoftReferenceを検索し、SoftReferenceオブジェクトが保持するBitmapが利用可能かどうかを判断します。利用可能であれば直接返し、そうでなければnullを返します。2段階キャッシュでも画像が見つからない場合は、画像リソースを直接ロードします。

5.2 非常に多くの項目情報をロードする必要があるlistview、gridviewなどの場合

adapterのgetView関数にはconvertViewパラメータがあり、再利用可能なviewオブジェクトがあるかどうかを知らせてくれます。convertViewを使用しない場合、getViewが呼び出されるたびに毎回viewが再作成されます。これにより、以前のviewがまだ破棄されていない可能性があり、さらに新しいviewを作成し続けるとメモリが急増し、OOMを引き起こします。また、convertViewを再利用するとき、内部の元の画像などのリソースは所有者のないものになります。

ここでGoogle公式が推奨しているのは、「convertview＋静的クラスviewholder」です。

公式の説明は次のとおりです：

a. キャッシュされたconvertViewをgetView()メソッドに渡して再利用し、不要なビューのインフレートを避けます。

b. ViewHolderパターンを使用して不要なfindViewByIdの呼び出しを避けます。findViewByIdが多すぎるとパフォーマンスにも影響するためです。

 

ViewHolderクラスの役割：ViewHolderパターンは、getViewメソッドが返すビューのタグ（tag）にデータ構造を格納します。このデータ構造には、データをバインドしたいビューへの参照が含まれており、getView()を呼び出すたびにfindViewById()を呼び出すことを避けます。

6. メモリ制限を超えてメモリを割り当てる方法：

6.1 Native Cからメモリを割り当てます。NDK（ネイティブ開発キット）とJNIを使用すると、Cレベル（malloc/freeやnew/deleteなど）からメモリを割り当てることができ、このような割り当ては24MBの制限にカウントされません。これは事実です。ネイティブコードからメモリを割り当てるのはJavaの便宜のためですが、RAM内のデータ（画像データであっても）を格納するために使用できます。これは少し衝撃的です。

6.2 OpenGLのテクスチャを使用します。テクスチャメモリは制限にカウントされません。アプリケーションが実際にどれだけのメモリを割り当てたかを確認するには、android.os.Debug.getNativeHeapAllocatedSize()を使用できます。上記の2つのテクニックのいずれかを使用できるNexusデバイスを使えば、単一のフォアグラウンドプロセスに300MB（デフォルトの24MB制限の10倍以上）を簡単に割り当てることができます。上記からわかるように、ネイティブコードを使用したメモリ割り当ては24MBの制限内にはありません（OpenGLのテクスチャもネイティブコードを使用してメモリを割り当てます）。

ただし、これらの2つの方法のリスクは、ネイティブヒープがシステムの利用可能メモリ制限を超えてメモリを割り当てると、通常は直接クラッシュすることです。
