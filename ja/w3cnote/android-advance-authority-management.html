1.4 Android6.0権限管理-オープンソースフレームワークソースコード分析

はじめに

Android6.0というシステムにおいて迎えた最大の特徴は、何と言ってもその権限管理です。なぜなら、小猪がチュートリアルを書いた時点では6.0はまだ出ていなかったはずですが、Android6.0の普及に伴い、その権限管理は開発に必須のスキルであり、基礎でもあると感じているからです。

余談

このような開発に必須のスキルや、システムによるその簡略化操作については、多くのブロガーがすでに類似したブログを書いています。ここで私がまた冗長な話を書いても、やはり駄文になってしまう気がします。

  • Android 6.0 実行時権限処理の完全解析

  • Android 6.0: 動的権限管理の解決策

    ...

しかし、同じく基礎であり、同じく皆がAndroid6.0の権限管理に直面している中で、人によってその解決策は異なります。そこでこの記事では、GitHub上のいくつかのオープンソースフレームワークがどのようにこの権限管理を解決（カプセル化）しているかを、皆さんと一緒に分析してみましょう。

PermissionGen

鸿神の記事で比較的基本的な権限管理フレームワークが紹介されていました。それでは、このフレームワークを中心に探求し、他の人がどのように権限管理の問題を解決しているかを学びましょう。

GitHubへのポータル

使用方法

1. 以下のいずれかの方法で必要な権限を取得します

PermissionGen.with(MainActivity.this) .addRequestCode(100) .permissions( Manifest.permission.READ_CONTACTS, Manifest.permission.RECEIVE_SMS, Manifest.permission.WRITE_CONTACTS) .request();

or

PermissionGen.needPermission(ContactFragment.this, 100, new String[] { Manifest.permission.READ_CONTACTS, Manifest.permission.RECEIVE_SMS, Manifest.permission.WRITE_CONTACTS } );

2. オーバーライドonRequestPermissionsResultメソッド

@Override public void onRequestPermissionsResult(int requestCode, String[] permissions, int[] grantResults) { PermissionGen.onRequestPermissionsResult(this, requestCode, permissions, grantResults); }

3. コールバック

正しい場合：

@PermissionSuccess(requestCode = 100) public void doSomething(){ Toast.makeText(this, "Contact permission is granted", Toast.LENGTH_SHORT).show(); }

誤りの場合：

@PermissionFail(requestCode = 100) public void doFailSomething(){ Toast.makeText(this, "Contact permission is not granted", t.LENGTH_SHORT).show(); }

あるフレームワークは、シンプルな使い方の背後に、多くの場合非常に複雑なアーキテクチャやデザインパターンが隠されています。このアーキテクチャのコード量や難易度はそれほど大きくないので、ソースコードと合わせて読むとより良いでしょう。

基本分析

メンバー変数

//必要な権限を保存する private String[] mPermissions; //リクエストコード private int mRequestCode; //Activity または Fragment を保存する private Object object;

コンストラクタ

//コンストラクタをプライベート化しています private PermissionGen(Object object) { this.object = object; }

with メソッド

多くのオープンソースライブラリでよく使われる手法で、Activity や Fragment を渡すメソッドであり、コンストラクタを呼び出します。これは皆さんも簡単に理解できるはずです。

public static PermissionGen with(Activity activity){ return new PermissionGen(activity); } public static PermissionGen with(Fragment fragment){ return new PermissionGen(fragment); }

代入

オブジェクトができたので、次はオブジェクトのメンバー変数に値を代入します。

//もちろん、permissions を追加するもう一つの方法として needPermission がありますが、それは皆さん自身で考えてみてくださいね。 public PermissionGen permissions(String... permissions){ this.mPermissions = permissions; return this; } public PermissionGen addRequestCode(int requestCode){ this.mRequestCode = requestCode; return this; }

上記のいくつかの流れは非常にシンプルです。既存のライブラリを解析することに慣れているなら、こうした手法はもう珍しくないでしょう。次に、アノテーションとリフレクションを通じて権限申請とコールバックをどのように行っているのかを説明します。

核心分析

requestResult

使用方法の2番目のステップで呼び出したのは、PermissionGen.onRequestPermissionsResult(this, requestCode, permissions, grantResults);これはオーバーロードされたメソッドで、主に最初のパラメータが異なります。this は Fragment または Activity のオブジェクトを指すことができますが、最終的にはすべて1つのメソッドにコールバックされます。

public static void onRequestPermissionsResult(Activity activity, int requestCode, String[] permissions,int[] grantResults) { requestResult(activity, requestCode, permissions, grantResults); } public static void onRequestPermissionsResult(Fragment fragment, int requestCode, String[] permissions,int[] grantResults) { requestResult(fragment, requestCode, permissions, grantResults); }

最終的には以下のメソッドを呼び出します：

private static void requestResult(Object obj, int requestCode, String[] permissions,int[] grantResults){ List<String> deniedPermissions = new ArrayList<>(); for(int i=0; i<grantResults.length; i++){ //通過した各権限 if(grantResults[i] != PackageManager.PERMISSION_GRANTED){ deniedPermissions.add(permissions[i]); } } //通過していない権限があれば失敗 if(deniedPermissions.size() > 0){ doExecuteFail(obj, requestCode); } else { doExecuteSuccess(obj, requestCode); } }

アノテーションを使用したコールバック

成功時のコールバックメソッド

private static void doExecuteFail(Object activity, int requestCode) { //方法1 Method executeMethod = Utils.findMethodWithRequestCode(activity.getClass(),PermissionFail.class, requestCode); //方法2 executeMethod(activity, executeMethod); }

方法1：

public static <A extends Annotation> Method findMethodWithRequestCode(Class clazz,Class<A> annotation, int requestCode) { //このオブジェクト内のメソッドをループする for(Method method : clazz.getDeclaredMethods()){ //各メソッドのアノテーションが annotation（PermissionSuccess または PermissionFail）に一致するかどうかを判断する if(method.isAnnotationPresent(annotation)){ //最終的にこのメソッドを呼び出します。ここではコピーしません。非常にシンプルで、その requestCode を判断します。 if(isEqualRequestCodeFromAnntation(method, annotation, requestCode)){ return method; } } } return null; }

方法2：

リフレクションを通じて必要なメソッドを取得し、次にそのメソッドを実行します。

private static void executeMethod(Object activity, Method executeMethod) { if(executeMethod != null){ try { if(!executeMethod.isAccessible()) executeMethod.setAccessible(true); //このメソッドを実行する executeMethod.invoke(activity, null); } catch (IllegalAccessException e) { e.printStackTrace(); } catch (InvocationTargetException e) { e.printStackTrace(); } } }

とてもシンプルですよね。明快な数ステップです。そしてもう一度少し眺めてみましょう。PermisstionSuccess 与 PermisstionFail2つのクラス

@Target(ElementType.METHOD) @Retention(RetentionPolicy.RUNTIME) public @interface PermissionFail { int requestCode(); }

与

@Retention(RetentionPolicy.RUNTIME) @Target(ElementType.METHOD) public @interface PermissionSuccess { int requestCode(); }

要するに、2つの実行時アノテーションであり、パラメータは int 型です。ここまでで PermisstionGen フレームワークの解説は終了です。次は鸿神のフレームワークについて話しましょう。GitHubへのポータル

MPermissions

考え方は大同小異です。最大の違いは、後者がコンパイル時アノテーションを使用している点です。この特徴は多くのオープンソースフレームワークが採用しており、そのおかげでリフレクションによる効率低下の問題がありません。

使用方法

すべてのPermisstion関連するフレームワークの使い方は皆同じで、必要な権限をonRequestPermissionsResultその中で静的メソッドを呼び出し、最後にコールバックします。ですから、ここでは他人のコードをコピーして文字数を稼ぐようなことはせず、直接本題に入りましょう。

分析

依存関係コンパイル時アノテーションを使用しているため、依存関係が生じます。

permission-sample は permission-api（つまりlib）に依存 permission-lib は permission-annotation に依存 compile は permission-annotation に依存

アノテーションクラス

在 permission-annotation以下に3つのアノテーションクラスがあります

  • 権限付与成功PermissionGrant

    @Target(ElementType.METHOD) public @interface PermissionGrant{ int value(); }

  • 権限付与失敗PermissionDenied

    @Target(ElementType.METHOD) public @interface PermissionDenied { int value(); }

  • 拒否されたらリマインドする

    @Target(ElementType.METHOD) @Retention(RetentionPolicy.CLASS) public @interface ShowRequestPermissionRationale { int value(); }

上記のアノテーションプロセッサを完成させたら、次は [それ] にpermission-lib依存関係を追加します。依存関係を追加したら、[それ] を見てみましょう。permission-libのメインクラスです。【注：compileについては解説を省略しました。少し複雑なので、後日別の記事でコンパイル時アノテーションについて詳しく説明します】

requestPermissions

前のフレームワークと非常によく似たメソッドですが、チェーン式プログラミングを完全にやめて、3つのパラメータをまとめて渡しています。

public static void requestPermissions(Activity object, int requestCode, String... permissions){ _requestPermissions(object, requestCode, permissions); } public static void requestPermissions(Fragment object, int requestCode, String... permissions){ _requestPermissions(object, requestCode, permissions); }

これもオーバーロードであり、Activity と Fragment を区別し、最後に以下のメソッドを呼び出します。

private static void _requestPermissions(Object object, int requestCode, String... permissions){ if (!Utils.isOverMarshmallow()){ doExecuteSuccess(object, requestCode); return; } List<String> deniedPermissions = Utils.findDeniedPermissions(Utils.getActivity(object), permissions); if (deniedPermissions.size() > 0){ if (object instanceof Activity) { ((Activity) object).requestPermissions(deniedPermissions.toArray(new String[deniedPermissions.size()]), requestCode); } else if (object instanceof Fragment) { ((Fragment) object).requestPermissions(deniedPermissions.toArray(new String[deniedPermissions.size()]), requestCode); } else { throw new IllegalArgumentException(object.getClass().getName() + " is not supported!"); } } else { doExecuteSuccess(object, requestCode); } }

コードはいくつかの判断に過ぎないので、詳しくは説明しません。ただし、ここで少し余談をさせてください。外から見れば、みんなプログラマーであり、誰でも1つの機能（タスク）を実装できます。しかし優秀なプログラマーは、コードの論理判断に対してより多くの処理を行います。

権限を申請した後、当然 Activity でこのメソッドをオーバーライドし、同じように最後に [それ] を呼び出します。onRequestPermissionsResultそして、MPermissions.requestResultこのメソッドに進み、次はコールバックです。ここでは概要だけ説明します。前のフレームワークとほぼ同じだからです。

private static void requestResult(Object obj, int requestCode, String[] permissions, int[] grantResults) { List<String> deniedPermissions = new ArrayList<>(); for (int i = 0; i < grantResults.length; i++) { if (grantResults[i] != PackageManager.PERMISSION_GRANTED) { deniedPermissions.add(permissions[i]); } } if (deniedPermissions.size() > 0) { doExecuteFail(obj, requestCode); } else { doExecuteSuccess(obj, requestCode); } }

doExecuteFail と doExecuteSuccess

コールバックが成功するか失敗するかは、フレームワークは気にしません。フレームワークは取得したオブジェクトを強制的にキャストして呼び出すだけです。

private static void doExecuteSuccess(Object activity, int requestCode){ findPermissionProxy(activity).grant(activity, requestCode); } private static void doExecuteFail(Object activity, int requestCode){ findPermissionProxy(activity).denied(activity, requestCode); }

findPermissionProxy

private static PermissionProxy findPermissionProxy(Object activity) { try { Class clazz = activity.getClass(); Class injectorClazz = Class.forName(clazz.getName() + SUFFIX); return (PermissionProxy) injectorClazz.newInstance(); } catch (ClassNotFoundException e) { e.printStackTrace(); } catch (InstantiationException e) { e.printStackTrace(); } catch (IllegalAccessException e) { e.printStackTrace(); } throw new RuntimeException(String.format("can not find %s , something when compiler.", activity.getClass().getSimpleName() + SUFFIX)); }

与

public interface PermissionProxy<T> { void grant(T source, int requestCode); void denied(T source, int requestCode); void rationale(T source, int requestCode); boolean needShowRationale(int requestCode); }
