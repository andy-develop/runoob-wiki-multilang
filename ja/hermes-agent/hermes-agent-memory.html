Hermes Agent メモリシステム

Hermes の最も中核となる差別化能力はツール呼び出しではなく、それは本当にあなたを覚えていることです。

ほとんどのAIツールは毎回の会話をゼロから始めます——今日1時間かけてあなたのプロジェクト構造、命名規則、デプロイ手順を教えても、明日新しいセッションを開けば、すべてやり直しです。

この章では、Hermes が3層メモリ構造によってこの問題をどのように解決するか、そして Agent がどのように自律的にメモリを管理し、セッションをまたいだ検索と再呼び出しを実現するかを詳しく解説します。

3層メモリアーキテクチャ

Hermes は、相互に独立し機能が補完し合う3層のメモリ構造を使用して、情報を保存および再呼び出しします。

3層設計の核となる考え方：高頻度で重要な情報はコンテキストに常駐させ、低頻度の履歴情報はオンデマンドで再呼び出しし、深層パターンは AI が自動的に推論する——メモリ能力と Token コストのバランスを取ります。

┌─────────────────────────────────────────────────┐
│       第一层：持久记忆（Persistent Memory）        │
│  MEMORY.md（环境事实）+ USER.md（用户画像）          │
│  → 每次会话启动时自动注入系统提示词，始终可见          │
├─────────────────────────────────────────────────┤
│       第二层：情节日志（Session History）            │
│  SQLite + FTS5 全文检索，存储所有历史对话             │
│  → Agent 主动搜索时按需加载，不占用固定 Token         │
├─────────────────────────────────────────────────┤
│       第三层：用户建模（Honcho，可选）               │
│  辩证推理引擎，提取跨会话模式、偏好与目标              │
│  → 比你亲口说出来的更深层地理解你                     │
└─────────────────────────────────────────────────┘
メモリ階層保存場所容量読み込み方法用途
永続メモリ~/.hermes/memories/ にある Markdown ファイル総量約1,300 tokensセッション開始時にシステムプロンプトへ自動注入重要な事実、常に可視
エピソードログSQLite データベース + JSONL 文字起こしファイル無制限（すべての過去の会話）Agent がオンデマンド検索、FTS5 全文検索特定の過去の議論を検索
Honcho ユーザーモデリングHoncho サーバーサイド APIAgent ごとに分離毎ターン/毎 N ターンのバックグラウンド推論で注入深層の好みと目標を自動推論

3層の間は代替関係ではなく、補完関係です。永続メモリは「私は常にこれらを知っておく必要がある」に答え、エピソードログは「先週この問題について話しましたか」に答え、Honcho は「あなたが本当に望んでいることは何か」に答えます。

永続メモリファイル

永続メモリは Hermes メモリシステムの第一層であり、最も基本的な層です。

それは、次の場所に保存された2つの~/.hermes/memories/下の Markdown ファイルで構成され、セッション開始時に自動的にシステムプロンプトへ注入されます。

2つのコアファイル

2つのファイルはそれぞれ役割を担い、互いに重複しません。

ファイル用途文字数上限約
MEMORY.mdAgent の個人ノート——環境の事実、プロジェクト規範、仕事で学んだこと2,200 文字~800 tokens
USER.mdユーザープロファイル——あなたの好み、コミュニケーションスタイル、仕事の習慣、スキルレベル1,375 文字~500 tokens

文字数上限は意図的に設計されています。メモリ内容が簡潔で焦点が絞られた状態を保証するためです。新しいエントリが上限を超える場合、memory ツールはエラーを返し、古いエントリを黙って破棄するのではなく、Agent に先にスペースを整理してから書き込むように指示します。

メモリがシステムプロンプトにどのように注入されるか

セッション開始時に、2つのファイルの内容が固定された形式でシステムプロンプトへ注入されます。形式は次のとおりです：

══════════════════════════════════════════════
MEMORY（Agent 个人笔记）[67% — 1,474/2,200 字符]
══════════════════════════════════════════════
用户的项目是位于 ~/code/myapi 的 Rust Web 服务，使用 Axum + SQLx
§
本机运行 Ubuntu 22.04，已安装 Docker 和 Podman
§
用户偏好简洁回复，不喜欢冗长解释

ここにいくつかの重要な設計上の詳細があります：

フリーズスナップショットモード：システムプロンプト内のメモリ内容はセッション開始時に一度だけ取得され、途中では更新されません。

これは意図的な設計です。LLM のプレフィックスキャッシュ（Prompt Cache）を有効に保ち、Token コストを削減するためです。

Agent がセッション中にメモリを変更すると、変更は即座にディスクへ書き込まれますが、待つ必要があります。次回のセッション開始時までコンテキストには現れません。

使用量パーセンテージが表示されます：[67% — 1,474/2,200]Agent が常に残り容量を把握でき、上限に近づくと自主的に整理できます。

§ をエントリ区切り文字として使用：各メモリエントリは § で区切られ、エントリ自体は複数行のテキストにできます。

Agentがメモリをどのように操作するか

Agent は組み込みのmemoryツールでメモリを管理し、3つの操作をサポートします。

操作説明パラメータ
addメモリエントリを1つ追加target（memory/user）、content
replace既存エントリを置換（部分文字列マッチングで位置を特定）target、old_text、content
remove既存エントリを削除（部分文字列マッチングで位置を特定）target、old_text

注意：read 操作はありません——メモリ内容はセッション開始時にすでにシステムプロンプトへ注入されているため、Agent はコンテキスト内で直接それを確認でき、追加の読み取りは不要です。

replace 和 remove使用部分文字列マッチングエントリを特定します。完全なエントリテキストを提供する必要はありません：

例

# シナリオ：現在のメモリに「ユーザーはすべてのエディタでダークテーマを好む」がある
# より正確なバージョンに更新する必要がある
# 部分文字列マッチングで位置を特定——一意に識別できる断片を提供するだけでよい

memory(
    action="replace",
    target="memory",
    old_text="ダークテーマ",  # 一意の部分文字列だけで元のエントリを特定できる
    content="ユーザーは VS Code でライトテーマ、ターミナルでダークテーマを使用"  # 置換後の新しい内容
)

部分文字列が複数のエントリにマッチした場合、ツールはエラーを返し、より正確なマッチング文字列を要求します。

何を記憶すべきか、何を記憶すべきでないか

Agent は自動的に価値のある情報を判断して保存します。通常、明示的に要求する必要はありません。

ただし、判断基準を理解しておくと、Agent の動作を理解しやすくなり、必要に応じて手動で導くのに役立ちます。

memoryに積極的に保存すべきもの（環境と仕事）

以下のタイプの情報は Agent が MEMORY.md への書き込みをトリガーします：

タイプ例
環境の事実本機は Debian 12、PostgreSQL 16 を実行、Docker は Podman で代替
プロジェクト規範~/code/api は Go 1.22、sqlc クエリ、chi ルーティングを使用。テストは make test
ツールの経験staging サーバーの SSH ポートは 22 ではなく 2222、キーは ~/.ssh/staging_ed25519 にあります
修正記録sudo で Docker コマンドを実行しないでください。ユーザーは docker ユーザーグループに所属しています
作業を完了する2026-01-15 データベースを MySQL から PostgreSQL に移行完了

userに積極的に保存すべきもの（あなたについて）

以下のタイプの情報は Agent が USER.md に書き込むトリガーとなる：

タイプ例
身元情報氏名、役職、タイムゾーン
コミュニケーションの好み簡潔な返信を好み、明白な手順の説明は不要
嫌悪事項コードに過剰なコメントを入れない
仕事の習慣毎日午後3時まではメッセージを見ない
スキルレベルRust と Python に精通、Go は学習中

保存すべきでない内容

以下の内容は貴重な記憶スペースを占有する価値がない：

タイプ例理由
あまりにも曖昧ユーザーはプロジェクトを持っている情報量がなく、再利用できない
いつでも再検索可能Python 3.12 は f-string のネストをサポート検索すればよいので、スペースを取る価値がない
生データ大量のログ、コードブロック、データテーブル文字数制限を超え、構造化された記憶のほうが有用
一時的な内容今回のデバッグの一時ファイルパス次回は使えない
すでにコンテキストにある内容プロジェクトの SOUL.md、AGENTS.md にすでにある情報重複した注入はトークンを浪費する

良いメモリ vs 悪いメモリ

同じ情報でも、書き方が良ければ1件で10件分の価値があり、書き方が悪ければまったく価値がない。

評価例コメント
好ユーザーの macOS 14 Sonoma、Homebrew、Docker Desktop、シェルは oh-my-zsh 付きの zsh、エディタは VS Code + Vim キーバインド情報密度が高く、関連する事実がまとまっている
好プロジェクト ~/code/api は Go 1.22、DB クエリに sqlc、ルーティングに chi を使用。テスト：make test。CI：GitHub Actions具体的で実行可能な規範
好staging サーバー（10.0.1.50）の SSH ポートは 22 ではなく 2222、鍵は ~/.ssh/staging_ed25519文脈のある教訓で、落とし穴を回避できる
差ユーザーはプロジェクトを持っているあまりにも曖昧で、いかなる行動の指針にもならない
差2026年1月5日、ユーザーは ~/code/api にある自分のプロジェクトを確認するよう依頼し、Go 1.22 を使用していることがわかった……冗長すぎて、核心情報が叙述に埋もれている

メモリ容量管理

記憶ファイルには厳格な文字数上限があり、Agent は上限に近づいたら積極的に整理する必要がある。

上限に近づくとどうなるか

新しいエントリが文字数上限を超える場合、ツールは静かに切り詰めるのではなくエラーを返す：

{
  "success": false,
  "error": "Memory 已用 2,100/2,200 字符。新条目（250 字符）会超出上限。
            请先整理：用 replace 合并重叠条目，或 remove 过时条目，
            再重试——在同一轮对话中完成。",
  "current_entries": [
    "用户的 macOS 14 Sonoma，Homebrew，Docker Desktop",
    "项目 ~/code/api 使用 Go 1.22，sqlc 做 DB 查询"
  ],
  "usage": "2,100/2,200"
}

このエラーを受け取った後の Agent の正しい対処法：

  1. 現在のすべてのエントリを読み取る（エラー応答にすでに含まれている）
  2. 削除または統合できるエントリを見つける
  3. 用 replace関連する複数のエントリをより簡潔な1件に統合する
  4. その後、新しいエントリの追加を再試行する

ベストプラクティス：システムプロンプトで記憶使用率が80%を超えたら、エラーを待たずに積極的に整理する。予防は常に修正よりもトークンを節約できる。

容量の参考

ストレージ上限一般的なエントリ数
MEMORY.md2,200 文字8〜15件
USER.md1,375 文字5〜10件

メモリ書き込み権限の制御

デフォルトでは、Agent は自由に記憶を書き込める——以下を含むバックグラウンドで自動実行される自己改善レビュー（1ラウンドの会話終了後にバックグラウンドで実行され、記憶とスキルを抽出する）。

何かを記憶に書き込む前に審査したい場合は、書き込み承認を有効にできる。

書き込み承認の有効化

設定ファイルで設定するだけ：

例

# ファイルパス：~/.hermes/config.yaml
# 記憶書き込み承認を有効化——すべての書き込み操作に手動承認が必要
memory:
  write_approval: true   # デフォルト false（自由書き込み）

有効化後の動作の変化：

シナリオ動作
CLI 対話中に Agent が記憶を書き込む場合ターミナルでインライン承認を求める
メッセージプラットフォーム / バックグラウンド自動レビュー書き込みは保留され、手動承認を待つ

承認管理コマンド

以下のスラッシュコマンドで保留中の記憶書き込みを管理する：

例

# 保留中の記憶書き込みを表示（自動トリガーは [auto] と表示）
/memory pending

# 指定した ID の書き込みを承認、またはすべて承認
/memory approve <id>
/memory approve all

# 指定した ID の書き込みを拒否、またはすべて拒否
/memory reject <id>
/memory reject all

# 実行時に承認をオンまたはオフにする（設定は永続保存される）
/memory approval on
/memory approval off

適用シナリオ：Agent があなたについて誤った仮定を保存した場合、または記憶内容を完全に管理したい場合、write_approval を有効にするのが最も直接的な方法です。

バックグラウンド自己改善レビューについて

各ラウンドの会話終了後、Hermes はバックグラウンドで自己改善レビュー（background review）を1回実行し、この会話を分析して保存に値する記憶やスキルを抽出します。

デフォルトではチャットに1行の通知が表示されますMemory updated。

通知の詳細度を調整できます：

例

# ファイルパス：~/.hermes/config.yaml
# バックグラウンドレビューの通知詳細度を制御
display:
  memory_notifications: on      # off | on（デフォルト）| verbose
值効果
off通知は表示されないが、レビューは引き続き実行され、書き込みも行われる
on（デフォルト）短い通知、例：Memory updated
verbose変更プレビューを含む、例：Memory + ユーザーは簡潔な返信を好む

メインモデルのコストが高い場合、バックグラウンドレビューをより安価なモデルで実行できます：

例

# ファイルパス：~/.hermes/config.yaml
# バックグラウンドレビューは独立したモデルを使用し、コストを削減
auxiliary:
  background_review:
    provider: openrouter
    model: google/gemini-3-flash-preview   # デフォルト auto = メインモデル

エピソードログとセッション横断検索

第2層の記憶——セッション履歴（Session History）——すべての過去の会話の完全な記録を保存し、全文検索とオンデマンド呼び出しをサポートします。

すべての会話は自動保存されます

すべてのセッション——CLI、Telegram、Discord、その他どのプラットフォームからのものであっても——自動的に2か所に保存されます：

保存場所形式内容
~/.hermes/state.dbSQLite データベース + FTS5 全文インデックス構造化メタデータ、完全なメッセージ履歴（ツール呼び出しと結果を含む）、トークン使用量、タイムスタンプ
~/.hermes/sessions/JSONL トランスクリプトファイルツール呼び出し記録を含む生の会話トランスクリプト

session_search ツール

Agent 組み込みsession_searchすべての過去の会話に対して全文検索を実行できるツール。

検索段階では LLM を介さず、SQLite FTS5 エンジンが直接実行します：

ワークフロー：

  1. FTS5 が関連性順にマッチするメッセージを検索
  2. セッションごとにグループ化し、最も関連性の高いセッションをいくつか取得（デフォルト 3 つ）
  3. 各セッションの会話を読み込み、マッチ位置付近の約 10万文字を切り出す
  4. 軽量サマリーモデルで焦点を絞った要約を生成
  5. 各セッションの要約とコンテキストを Agent に返す

サポートされている検索構文（FTS5 標準）：

構文例説明
キーワード検索docker deploymentいずれかのキーワードを含むメッセージにマッチ
フレーズ一致"exact phrase"フレーズ全体に完全一致
ブール ORdocker OR kubernetesいずれかのキーワードにマッチ
ブール NOTpython NOT java特定のキーワードを除外
プレフィックスワイルドカードdeploy*deploy で始まる単語にマッチ

トリガータイミング：Agent は「前回話し合った……」や「以前のあの案……」に言及したときに、あなたに繰り返し説明させるのではなく、自動的に session_search を呼び出します。

session_search vs 永続メモリ

両者は補完関係にあり、置き換え関係ではありません：

比較軸永続記憶（MEMORY.md / USER.md）セッション履歴（Session Search）
容量合計約1,300トークン無制限（すべての過去の会話）
速度即時（システムプロンプトに含まれている）約20ms（FTS5クエリ）
トークンコストセッションごとに固定消費オンデマンド、検索しない限り消費しない
用途重要な事実、常に参照可能特定の過去の議論を検索
管理方法Agent が自発的に整理全自動、介入不要

記憶「常に知っておくべきこと」に使用——環境の事実、ユーザーの好み、プロジェクト規約。

セッション履歴「先週この問題について話しましたか？」に使用——具体的な過去の議論を検索します。

セッション管理

セッション履歴の各セッションには、名前付け、復元、エクスポート、クリーンアップが可能です。

命名と復元

Hermes は最初のターン後に短いセッションタイトル（3〜7語）を自動生成します。バックグラウンドで非同期に実行されるため、応答速度には影響しません。

手動で名前を付けることもできます：

例

# セッション内で手動タイトルを設定
/title 認証モジュールを再構築

名前を付けた後は、タイトルを直接使ってセッションを復元できます：

例

# タイトルでセッションを復元
hermes -c "認証モジュールを再構築"

# 最新のセッションを復元
hermes --continue

# セッションIDで復元
hermes -r <session_id>

自動系譜（Auto-Lineage）：セッションがコンテキスト圧縮を受けると、Hermes は継続セッションを自動的に作成して番号を付けます：

"我的项目" → "我的项目 #2" → "我的项目 #3"

タイトルで復元する場合、最新の継続セッションが自動的に選択されます。

よく使うセッション管理コマンド

例

# 最近の20セッションを一覧表示
hermes sessions list

# ソースプラットフォームでフィルタリング
hermes sessions list --source telegram

# さらに多く表示
hermes sessions list --limit 50

# 指定したセッションの名前を変更
hermes sessions rename <id> "新しいタイトル"

# すべてのセッションをファイルにエクスポート
hermes sessions export backup.jsonl

# 指定したセッションを削除
hermes sessions delete <id>

# 30日以上前の古いセッションをクリーンアップ
hermes sessions prune --older-than 30

# 統計情報を表示
hermes sessions stats

hermes sessions listの出力例：

セッション自動クリーンアップ（オプション）

デフォルトではセッション履歴は永久に保持されます（session_search にデータを提供するため）。

自動クリーンアップが必要な場合は、設定で有効にします：

例

# ファイルパス: ~/.hermes/config.yaml
# セッション自動クリーンアップを有効化（デフォルトではオフ）
sessions:
  auto_prune: true        # デフォルトは false
  retention_days: 90      # 最近90日分を保持
  vacuum_after_prune: true
  min_interval_hours: 24

Honcho ユーザーモデリング

Honcho は Plastic Labs が開発した AI ネイティブな記憶バックエンドで、プラグインとして Hermes に統合されています。

これは MEMORY.md と USER.md を置き換えるものではなく、その上に弁証法的推論レイヤーを追加します——あなたの会話パターンを分析し、明示的に表明していない好み、目標、習慣を自動的に推論します。

MEMORY.md の手動キュレーションとは異なり、Honcho は全自動です。各ターンの後に（頻度は設定可能）バックグラウンドで推論し、あなたへの理解を深めていきます。

Honcho と組み込みメモリの比較

機能内蔵記憶Honcho
セッション間の永続化ローカルファイルサーバーサイド API
ユーザープロファイル手動キュレーション（USER.md）自動弁証法的推論
セッション要約—セッションレベルのコンテキスト注入
マルチAgent分離—Agent ごとに個別モデリング
セマンティック検索FTS5 全文推論結果に基づく

2層のコンテキスト注入

各ターンで、Honcho は2層のコンテキストを組み立ててシステムプロンプトに注入します：

基本レイヤー（Base Context）：セッション要約 + ユーザー表現 + ユーザー Peer Card + AI 自己表現。contextCadence（Nターンごと）で一度更新されます。これは「このユーザーは誰か」のレイヤーです。

弁証法レイヤー（Dialectic Supplement）：Honcho の LLM エンジンによるリアルタイム推論で生成され、「現在最も関連性が高いものは何か」に焦点を当てます。dialecticCadence に従って更新されます。

弁証法的推論の2つの起動モード：

モード条件クエリ方法
コールドスタート履歴データなし汎用クエリ——「このユーザーは誰か？その好み、目標、仕事の進め方は何か？」
ウォームスタート履歴データありセッション焦点クエリ——「今回のセッションで話し合われた内容に基づくと、このユーザーに関して最も関連性の高いコンテキストは何か？」

3つの独立した調整ノブ

パラメータ制御する内容デフォルト値
contextCadence基本レイヤー更新間隔（NターンごとにAPIを1回呼び出し）1
dialecticCadence弁証法レイヤー更新間隔（NターンごとにLLMを1回呼び出し）2（推奨 1〜5）
dialecticDepth各弁証的推論の深さ（1〜3回のパス）1

3つのノブは完全に独立しています——基本レイヤーを高頻度で更新し、弁証的推論を低頻度で実行することも、その逆も可能です：

例

{
  "contextCadence": 1,
  "dialecticCadence": 5,
  "dialecticDepth": 2
}

上記の設定は次の意味です：毎ターン基本レイヤーを更新し、5ターンごとに2パス深度の弁証的推論を行います。

マルチパス弁証法的推論

dialecticDepth が1より大きい場合、各弁証的推論で複数回の LLM 呼び出しが実行されます：

Passタスク説明
Pass 0コールド/ウォームスタート推論初期評価の確立
Pass 1自己監査初期評価の盲点を特定し、最近のセッション証拠を総合
Pass 2調和前2ラウンドの矛盾を確認し、最終的な総合結論を生成

深さ3は必ずしも3回の LLM 呼び出しを意味しません——前のラウンドで高品質な出力が得られた場合、次のラウンドは早期終了し、トークンを節約します。

Honcho クイックスタート

例

# 対話式セットアップで honcho プロバイダーを選択
hermes memory setup

または手動で設定：

例

# ファイルパス: ~/.hermes/config.yaml
# Honcho を記憶プロバイダーとして有効化
memory:
  provider: honcho

例

# APIキーを環境変数ファイルに書き込む
echo 'HONCHO_API_KEY=your_key' >> ~/.hermes/.env

honcho.dev で APIキーを取得します。

Honcho が提供するツール

Honcho を有効にすると、Agent は5つの専用ツールを使用できます：

ツール用途
honcho_profileユーザー Peer Card の読み取りまたは更新
honcho_search推論結果に基づくセマンティック検索（生の断片、LLM による総合なし）
honcho_context完全なセッションコンテキストの取得（要約、ユーザー表現、最近のメッセージ）
honcho_reasoningHoncho LLM 推論の呼び出し（reasoning_level を指定可能）
honcho_conclude推論結論の作成または削除

Honcho CLI コマンド

例

# Honcho の接続状態、設定、主要な設定を表示

# セッションポリシーの表示または設定
hermes honcho strategy

# リコールモードの表示または設定（hybrid/context/tools）

# トークン予算の表示または設定

# 既知の Honcho セッションマッピングを一覧表示
hermes honcho sessions

メモリシステム設定リファレンス

以下は、すべての記憶関連設定の完全なリファレンスです。設定ファイルに直接コピーして使用できます。

例

# ============================================
# ファイルパス: ~/.hermes/config.yaml
# Hermes 記憶システム完全設定リファレンス
# ============================================

# --- 永続記憶設定 ---
memory:
  memory_enabled: true          # 永続メモリ（MEMORY.md）を有効にするかどうか
  user_profile_enabled: true    # ユーザープロファイル（USER.md）を有効にするかどうか
  memory_char_limit: 2200       # MEMORY.md の文字数上限（約800トークン）
  user_char_limit: 1375         # USER.md の文字数上限（約500トークン）
  write_approval: false         # true = すべてのメモリ書き込みに手動承認が必要
  provider: honcho              # オプション：Honcho メモリプロバイダーを有効にする

# --- セッション自動クリーンアップ（オプション、デフォルトではオフ）---
sessions:
  auto_prune: false             # 古いセッションを自動クリーンアップするかどうか
  retention_days: 90            # 直近 N 日間のセッションを保持
  vacuum_after_prune: true      # クリーンアップ後にディスク領域を回収するかどうか
  min_interval_hours: 24        # 2回のクリーンアップ間の最小間隔

# --- バックグラウンドレビュー通知 ---
display:
  memory_notifications: on      # off | on | verbose

# --- バックグラウンドレビューでより安価なモデルを使用（オプション）---
auxiliary:
  background_review:
    provider: openrouter        # モデルプロバイダー
    model: google/gemini-3-flash-preview  # モデル名

# メモリを追加
覚えておいて：このプロジェクトでは依存関係の管理に Poetry を使用し、pip は使いません

# メモリを削除または上書き
MySQL に関する以前の記録は忘れてください。PostgreSQL に移行しました

# メモリ内の情報を更新
ステージングサーバーの IP を 10.0.2.100 に更新してください

# メモリを照会
あなたが今、私についてどんな情報を覚えているか教えてください

スラッシュコマンド

例

# 現在のメモリ内容を表示
/memory

# 承認待ちの書き込みを表示
/memory pending

# 承認待ちをすべて承認
/memory approve all

# 承認待ちをすべて拒否
/memory reject all

# 書き込み承認を有効化
/memory approval on

# 書き込み承認を無効化
/memory approval off

メモリファイルを直接編集する

メモリファイルはプレーンな Markdown なので、エディタで直接開いて修正できます：

例

# 現在のメモリ内容を表示
cat ~/.hermes/memories/MEMORY.md
cat ~/.hermes/memories/USER.md

# エディタで開いて修正
nano ~/.hermes/memories/MEMORY.md

注意：ファイルを直接編集した場合、変更は次回のセッション起動時に有効になり、現在のセッションのコンテキストにはすぐには反映されません。

メモリのセキュリティとプライバシー

セキュリティスキャン

メモリコンテンツは書き込み前にセキュリティスキャンを受け、インジェクション攻撃やデータ窃取パターンを検出します。

システムは以下の脅威パターンを検出します：

脅威タイプ検出内容
プロンプトインジェクションAgent のシステム命令を上書きしようとするインジェクションパターン
認証情報の窃取Agent に API キーやトークンの漏えいを誘導する命令
バックドアのインストールSSH バックドアやリモートアクセスのインストール命令
隠し文字不可視の Unicode 文字（ゼロ幅スペース、方向オーバーライドなど）

脅威パターンに一致するコンテンツは書き込みが拒否されます。

ログ内の機密情報のマスキング

API キー、トークンなどの機密情報は、すべてのログファイルで自動的にマスキングされます。ツール出力に現れた場合でも、平文では記録されません：

例

# ファイルパス：~/.hermes/config.yaml
# デフォルトで有効、機密情報は自動的にマスキングされます
security:
  redact_secrets: true

データのローカル保存

すべてのメモリデータ（MEMORY.md、USER.md、state.db）はデフォルトでローカルの~/.hermes/ディレクトリに保存され、クラウドにはアップロードされません。

Honcho を使用することを選択した場合、会話データは処理のために Honcho のサーバーに送信されます。これは意図的なトレードオフです：データのアップロードと引き換えに、より深い推論能力を得るためです。
