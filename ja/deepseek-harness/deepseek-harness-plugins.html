DeepSeek Harness コミュニティプラグイン

DeepSeek Harness（略称 dsh）の核となる設計それは Everything is a Plugin（すべてがプラグイン）です。

dsh では、モデルアダプタ、ツール登録、セッションログ、Agent Loop、サンドボックス、ストレージ、タスクスケジューリング、UI、さらには権限ポリシーまでもが Cordis プラグインとして存在できます。

Cordis は軽量なプラグイン化アプリケーションフレームワークであり、プラグインの登録、依存関係の解決、ライフサイクル管理を統一的に担当します。

DeepSeek Harness は機能が固定された Agent ではなく、継続的に組み立てられる Agent インフラストラクチャに近いものです。

従来の LLM Agent の構造は通常比較的固定されており、Prompt、モデル、Agent、ツールが順に直列に接続され、能力のほとんどはフレームワークのコアにカプセル化されています。

より正確な理解の仕方は、dsh は多くの機能を内蔵した Agent ではなく、プラグインを通じて Agent の能力を継続的に組み立てられるランタイムである、ということです。。

dsh のコアソースコードを変更することなく、その動作を変更できます。

よくあるニーズと対応する方法は次の通りです：

ニーズ方法対応するプラグイン例
インターフェースを変更する UI プラグインをインストールする dsh-web-ui、dsh-TUI
ビジョン機能を追加する ビジョンプラグインをインストールする modlens、dsh-vision-toolkit
マルチエージェント協働 Agent Teams プラグインをインストールする dsh-agent-teams
ブラウザ自動化 Browser プラグインをインストールする dsh-browser、BrowserSkill
コンテキスト管理 Context プラグインをインストールする dsh-context

プラグイン同士を重ね合わせることで、まったく異なる作業環境を形成することもできます。

dsh では、モデルアダプタ、ツールレジストリ、セッションログ、Agent Loop、サンドボックス、ストレージ、スケジューリング、UI、さらには権限ポリシーまで、すべて Cordis プラグインの形で存在します。

次の図は dsh の全体的なプラグイン構造を示しています。ホストは能力の組織化のみを担当し、能力自体はすべてプラグインが提供します：

Profile：プラグインが実行される環境を決定します

dsh のプラグインインストールには、通常の npm パッケージや Python パッケージとの明確な違いがあります。プラグインをインストールした後、どの環境で実行されるかは Profile が決定します。

同じ dsh でも使用シナリオに応じて異なるプラグイン構成をロードでき、異なる Profile 間で相互に干渉しません。

よく使われる 3 つの Profile は次の通りです：

Profile形態適用シナリオ
web ブラウザでアクセスする Web ワークベンチ 日常的な対話開発、タスクボード、リモートアクセス
tui 端末の全画面インターフェース SSH リモート開発、コマンドラインに慣れたユーザー
headless 画面なしのバックグラウンド実行 自動化スクリプト、CI 統合、定期タスク

例えば、典型的な Web Profile のプラグイン構成：

Web Profile
├── dsh-web-ui          # Web 工作台
├── dsh-better-sidebar  # 侧边栏工作区
├── modlens             # 视觉能力
└── dsh-market          # 插件市场

一方、端末ユーザーは次のものだけを残すかもしれません：

TUI Profile
└── dsh-TUI             # 全屏终端界面

プラグインのインストール

dsh はプラグインに統一されたインストール入口を提供しており、1 つのコマンドで完了できます。

# 安装插件到 web profile（--profile 指定目标环境，必填）
dsh plugin --profile web add <源>

# 安装插件到 tui 终端环境
dsh plugin --profile tui add <源>

dsh-web-ui（オープンソースアドレスhttps://github.com/zhu1090093659/dsh-web-ui）のインストールを例にします：

dsh plugin --profile web add @linxin666/dsh-web-ui-all@latest

インストール後、再起動すると、設定のプラグインリストでインストール済みプラグインを確認できます：

その後、左側のリストでプラグインの機能を確認したり、スキンを試しにインストールしたりできます：

完全なインストールフローは通常次の通りです：

选择 Profile
    ↓
安装插件
    ↓
检查依赖 / README
    ↓

    ↓
验证插件是否加载

UI 拡張とワークベンチ

この種類のプラグインは「インターフェースが使いにくい」という問題を解決し、dsh をコマンドラインツールから IDE に近い完全なワークベンチへとアップグレードします。

その中でも dsh-web-ui と DSH-better-sidebar はコミュニティで最も人気のある組み合わせです。前者は Web インターフェースの機能面を補完し、後者は常駐サイドバーを提供します。

プラグイン概要インストールコマンド
dsh-web-ui Web UI オールインワン：タスクボード、Git グラフ、右側パネル、リモートモバイル、デスクトップペット、リアルタイム Token 統計、スキンセンター dsh plugin --profile web add github:zhu1090093659/dsh-web-ui
DSH-better-sidebar 完全なサイドバーワークベンチ：ファイルツリー / エディタ、ターミナル、Git、サブエージェント、サードパーティプラグインによる新規 Tab 登録をサポート dsh plugin --profile web add dsh-better-sidebar
dsh-TUI Claude Code スタイルの全画面ターミナル TUI：ストリーミング思考、Esc ダブルクリックで遡上、ステータスバー、モデル切り替え dsh plugin --profile tui add @deepseek-harness-tui/dsh-tui
dsh-at-file 入力ボックスで @ を入力してワークスペースのファイル / ディレクトリをすばやく検索・参照 dsh plugin --profile web add github:omdsh-dev/dsh-at-file

dsh-web-ui は単にインターフェースを変えるだけでなく、Agent ワークフローに合わせてタスクボード、Git グラフなどのワークベンチ機能を補完します。

DSH-better-sidebar は「ワークスペースの組織化能力」の問題を解決し、dsh を「AI IDE」にしたいユーザーに適しています。

dsh-at-file の使い方は非常に直感的で、入力ボックスに @ を入力するとワークスペースのファイルを検索・参照できます：

请分析 @runoob-demo/src/main.py

比较 @runoob-demo/src/api 和 @runoob-demo/src/service

コード Agent にとって、この操作はファイル内容を手動でコピーするよりもはるかに自然です。

端末ユーザーには dsh-TUI がおすすめです。ターミナルでストリーミング出力とメッセージ遡上を提供し、体験は Claude Code に近いものです。

ビジョンとマルチモーダル

dsh はプラグインを通じて、本来テキスト中心の Agent に視覚処理能力を「外付け」できます。

modlens の核となる考え方は、画像を構造化された視覚的エビデンスに変換し、それをテキストモデルに処理させることです。

同じように Web ページのスクリーンショットを貼り付けても、得られるのは「これは Web ページのスクリーンショットです」ではなく、OCR テキスト、レイアウト情報、座標、意味ラベルの組み合わせです。

プラグイン概要インストールコマンド
modlens テキストのみのモデルが瞬時にマルチモーダル化：画像を貼り付けると構造化された OCR、レイアウト、意味的エビデンスを出力 dsh plugin --profile web add @liustack/modlens
dsh-vision-toolkit 完全なビジョンツールボックス：意図の Q&A、長いスクリーンショットの OCR、UI 再現、grounding、ピクセル diff dsh plugin --profile web add @anionex/dsh-vision-toolkit
dsh-vision-router 無料のビジョンチェーンとピクセルレベルツール、ローカルの Ollama / LM Studio をサポート dsh plugin --profile web add dsh-vision-router

この種のプラグインは、OCR、Web ページのスクリーンショット分析、ドキュメント理解、画像コンテンツ抽出などのタスクに適しています。

主な作業がフロントエンド開発、UI の再現、スクリーンショット分析に関わる場合、dsh-vision-toolkit は単純な OCR よりも実用的です。

視覚能力を完全にローカルにデプロイしたいユーザーは、dsh-vision-router に注目するとよいでしょう。

スキン、テーマ、デスクトップペット

この種のプラグインは Agent の核となる能力を必ずしも高めるわけではありませんが、「すべてがプラグイン」という徹底ぶりを最もよく示しています。スキンやデスクトップペットまでもがプラグインなのです。

プラグイン概要インストールコマンド
dsh-deep-whale クジラ娘スキンシリーズ（深海メイド工房など）、ライト / ダークモード対応 dsh plugin --profile web add github:Small-tailqwq/dsh-deep-whale
whale-girl / dsh-pet シリーズ ドラッグ、給餌、インタラクションが可能なデスクトップペットの小クジラ（コミュニティの複数リポジトリ） 各リポジトリの README に従ってインストール

Agent ワークベンチが堅苦しいと感じるなら、この種のプラグインはまさに「プラグイン化」の娯楽的な証明です。

マルチエージェントとワークフロー

UI プラグインが「dsh の使い方」を解決するのに対し、マルチエージェントプラグインは「複数の Agent にどう一緒に作業させるか」を解決します。

dsh-agent-teams の考え方は非常に直感的です。現在のセッションがリーダー役となり、タスクを複数の対話を継続できる子 Agent に分割します。

プラグイン概要インストールコマンド
dsh-agent-teams 現在のセッションがリーダーに：継続対話可能な子 Agent の作成、依存関係のあるタスク、自動スケジューリング、リアルタイムパネル dsh plugin --profile web add @nanmicoder/dsh-agent-teams
dsh_workflow 生成、保存、復元、観察、ガバナンスが可能な Workflow 層 dsh plugin --profile web add "github:dsh-external/dsh_workflow#main"

両者の役割分担は次のように理解できる：agent-teams は「複数の Agent が一緒に働く」ことを解決し、workflow は「Agent のワークフローを固定化して繰り返し実行する」ことを解決する。

組み合わせることで、完全な実行チェーンを形成できる：

需求
 ↓
Leader Agent（任务拆分）
 ├── Frontend Agent
 ├── Backend Agent
 ├── Test Agent
 └── Review Agent
 ↓
Workflow（流程固化、反复执行）
 ↓
最终结果

このとき dsh は「AI がコードを書くのを手伝う」から、「AI Agent が自ら複数の実行ユニットを組織してタスクを完了する」へと徐々に変わっていく。

ブラウザと自動化

Agent が実際に本番環境に入った後、コードの読み書きだけでは不十分なことが多く、Web ページを開く、ページを読み取る、クリックや入力を行う、ログイン状態を維持したままタスクを実行することも必要になる。

ヘッドレスブラウザ方式とは異なり、dsh-browser はローカルの Chrome を直接操作するため、既存のログイン状態と Cookie がすべて保持され、Agent は毎回ゼロからログインする必要がない。

プラグイン概要インストールコマンド
dsh-browser 実際の Chrome を操作（ログイン / Cookie 保持）、構造化テキストで Web ページを制御 リポジトリはワンクリックインストールスクリプト（ブラウザ拡張機能含む）を提供
BrowserSkill テンセントがオープンソース化した、実際にログイン済みのブラウザ自動化ソリューション（CLI + 拡張機能） リポジトリの説明に従ってインストール

ブラウザプラグインは、サイト自動化、バックエンド操作、データ収集、Web テストなど、ログイン状態が必要なタスクに適している。

この種のプラグインは通常、ブラウザ拡張機能などの追加コンポーネントも含むため、手動でコマンドを組み立てるのではなく、公式スクリプトまたは README に従ってインストールすることを推奨する。

メモリ、コンテキスト、セッション移行

Agent を長く使うほど、本当の問題はモデルが十分賢くないことではなく、コンテキストがどんどん乱れていくことである場合が多い。

この種のプラグインは「コンテキスト」を中心に機能する：他の場所のセッションを取り込むか、現在のコンテキストの構成を明確にするかのいずれかである。

プラグイン概要インストールコマンド
dsh-chat-import Claude Code / Codex / ChatGPT / Cursor / Gemini などから履歴セッションをロスレスでインポート dsh plugin --profile web add dsh-chat-import
dsh-context コンテキスト構成、Token トレンド、圧縮 / トリミングの可視化パネル dsh plugin --profile web add dsh-context

これまで他の Coding Agent を大量に使用してきた場合、dsh-chat-import のような移行プラグインは非常に価値がある。

長時間稼働する Coding Agent にとって、コンテキスト管理の重要性はますます高まるだろう。

Agent の効果は、単にモデルの benchmark を見るのではなく、「モデル能力 + コンテキスト品質 + ツール能力 + タスク状態」に大きく依存する。

プラグインの発見と管理

プラグインの数が増えてくると、新たな問題が生じる：プラグインをどこで探すか、である。

dsh-market は設定ページにプラグインマーケットを内蔵しており、検索、分類、ワンクリックでのインストール / 更新をサポートしている。dsh-find-plugin はさらに進んで、セッション内で自然言語を使って直接プラグインを探せる。

プラグイン概要インストールコマンド
dsh-market / dshmarket 設定ページにプラグインマーケットを内蔵：検索、分類、ワンクリックインストール / 更新 dsh plugin --profile web add dshmarket
dsh-find-plugin セッション内で自然言語によりプラグインを検索し、説明とインストールコマンドを返す dsh plugin --profile web add dsh-find-plugin

例えば「Web ページのスクリーンショットを分析できるプラグインはありますか」と直接質問すると、プラグイン名、機能説明、インストールコマンドが返ってくる。

dsh を長期的に使用する予定なら、最初に手動で何十もの GitHub リポジトリを検索するのではなく、まずプラグインマーケットを調べることを推奨する。

「プラグインを探す」こと自体もプラグインである。これはまさに Everything is a Plugin という設計思想の直接的な現れである。

その他の実用プラグイン

上記の主要カテゴリのほかにも、コミュニティには注目度が低くなく、分類しにくいプロジェクトがいくつかある。

プラグイン概要インストールコマンド
deepseek-harness デスクトップ版 デスクトップクライアント、ワンクリック起動 ダウンロードしてインストール
DeepSeek Harness プラグイン厳選リスト 厳選されたプラグインリストをいくつか収集 プラグインのドキュメントの説明に従ってインストール
archify 美しく検証可能なアーキテクチャ図 / フローチャートを生成（Skill 形式） リポジトリの Skill インストール方法に従う
dsh-plugin-subscriptions OAuth ログインにより、dsh で既存の ChatGPT / Claude / Grok サブスクリプションを再利用（コミュニティリポジトリ） リポジトリの README に従ってインストール

デスクトップクライアントは、コマンドラインや実行環境を自分で扱いたくないユーザーに適しており、archify は Agent にコードリポジトリの分析やシステムアーキテクチャの設計を頻繁に任せるユーザーにとって有用である。

サブスクリプション系プラグインはアカウント認証と第三者サービスに関わるため、セキュリティリスクが通常の UI プラグインより明らかに高い。「無料モデル」「無料サブスクリプション」などのキーワードだけでインストールせず、必ずソースコード、権限範囲、実際の認証フローを確認すること。

シナリオ別のおすすめ

dsh の強みは「プラグインが多いほど強い」ことではなく、自分のワークフローに合わせて自由に組み合わせられることである。

最初から十数個のプラグインをインストールするのではなく、以下のいくつかの典型的なシナリオに従って構築するとよい。

使用シナリオ推奨構成カバーする機能
使い始めたばかりのスタート構成 dsh-web-ui + DSH-better-sidebar + dsh-market + modlens ワークスペース + サイドバー + プラグインマーケット + ビジュアル
ターミナル派 dsh-TUI 全画面ターミナルインターフェース、ストリーミング思考、メッセージ遡及
マルチ Agent 開発 dsh-agent-teams + dsh_workflow タスク分割、自動スケジューリング、プロセス固定化
他のツールからの移行 dsh-chat-import + dsh-at-file + dsh-context 履歴セッションのインポート、ファイルのクイック参照、コンテキスト管理

スタート時のアドバイス：まず dsh-market をインストールし、次にマーケットを通じて必要なプラグインをインストールする。その後の更新管理もまとめて任せるとよい。

まずコアワークフローを動かせるようにし、その後で徐々に他の機能を追加していく。

サードパーティ製プラグインをインストールする際の注意事項

dsh プラグインエコシステムの最大の利点は、同時に最大のリスクでもある：プラグインは非常に大きな拡張能力を持つということだ。

UI スキンプラグインとブラウザ自動化プラグインでは、セキュリティレベルが明らかに異なる。インストール前には少なくとも以下の4項目を確認すること。

まずソースコードを確認する

特に Shell、ブラウザ、OAuth、API Key、ファイルシステム、ネットワーク権限に関わるプラグインは重点的に審査すること。

README の宣伝文句だけを見ないこと。

ライセンスを確認する

プロジェクトが採用している License を確認する。

商用利用、二次開発、企業内デプロイを予定している場合は、ライセンスの制約を事前に確認することがさらに重要である。

依存関係を確認する

npm / Python の依存関係、ブラウザ拡張機能、外部サービスを重点的に確認する。

一見 UI プラグインにすぎないプロジェクトでも、不必要な依存関係が大量に導入されている場合は警戒に値する。

バージョンや Commit を固定する

dsh は依然として急速な反復段階にあり、コミュニティプラグインの API も変更される可能性がある。本番環境では常に latest や main を追跡することは推奨しない。

# 不推荐：始终追踪 main 分支
github:dsh-external/dsh_workflow#main

# 推荐：固定到具体 commit（具体语法以插件管理器当前版本为准）
github:xxx/xxx@a1b2c3d

これにより、「今日は動いていたのに、プラグイン作者が更新したら明日突然壊れる」という状況を避けられる。

さらに多くのプラグインを探索したい場合は、以下のチャネルから始めるとよい：

チャネル説明

awesome-dsh-plugin コミュニティが維持する厳選プラグインリスト
dshhub.dev、dsh.so コミュニティプラグインディレクトリサイト

プラグイン化の背後にあるアーキテクチャ思想

dsh を単に「DeepSeek が作った Claude Code に似た Agent ツール」と見なすのは、実際には過小評価である。

従来の Agent は Model、Tool、Memory、Loop、UI をすべて自身の内部にカプセル化していたが、Harness は「能力を組織化すること」だけを担当し、能力を固定化しない。

これは、将来コミュニティで本当に競われるのは、誰がより美しいチャットウィンドウを書いたかではなく、誰がより優れた基盤能力プラグインを提供できるかである可能性を示している：

能力の側面説明
Agent Loopセッションループと実行戦略
Coding Agentコードの理解と生成
Browser AgentWeb ページ操作と自動化
Memory長期メモリ管理
Context Engineeringコンテキストの整理と圧縮
Multi-Agentマルチエージェント協調
Workflowプロセスオーケストレーションとガバナンス
Evaluation効果評価
Sandbox安全な分離実行
Tool Routerツールルーティング
Model Routerモデルルーティング

最終的に形成されるのは、単一の Agent 製品ではなく、Agent Plugin Ecosystem（プラグイン化された Agent エコシステム）である可能性が高い。

段階的に自分専用の Agent ランタイムを構築する

dsh の最も適した使い方は「インストール、起動、終了」ではなく、段階的な構築である。

安装 Harness
    ↓
选择 Profile
    ↓
安装基础插件
    ↓
搭建自己的工作台
    ↓
增加工具
    ↓
增加 Agent
    ↓
增加 Workflow
    ↓
增加 Memory / Context
    ↓
形成自己的 Agent Runtime

以前は AI プログラミングツールを選ぶ際、Claude Code、Codex、Cursor の間で選択していた。プラグイン化以降、考え方は変わり始めている：基盤となる Runtime は固定し、能力は自分で組み合わせるのである。

一人はWeb UIを選択でき、別の人はTUIを選択できる；ある人はブラウザを重点的に使い、ある人はマルチAgentを重点的に使い、さらには自分でプラグインを開発して、ツール、ワークフロー、またはAgentを統合することもできる。

コアランタイムは接続機能を担当し、プラグインは機能の提供を担当し、Profileは機能の組織化を担当し、開発者は最終的に自分自身のAgentを定義する責任を負う。

このエコシステムが発展し続ければ、dshは最終的に単なる「AIプログラミングツール」ではなく、組み合わせ可能なAgent Operating Environment（Agent実行環境）に近づくかもしれない。

そしてこれこそが、Everything is a Plugin が最も研究に値する点である。
